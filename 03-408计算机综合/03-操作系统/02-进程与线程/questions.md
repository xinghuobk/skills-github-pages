### 题 1

**题干**：一个进程在其生命周期内会在不同状态之间切换。下列关于进程状态转换的叙述中，错误的是

**选项**：
(A) 处于运行态的进程可能因等待I/O而转换为阻塞态
(B) 处于阻塞态的进程在等待的事件发生后会转换为就绪态
(C) 处于就绪态的进程获得CPU后会转换为运行态
(D) 处于运行态的进程不可能直接转换为就绪态

**标准答案**：$\boxed{D}$

**答案解析**：处于运行态的进程在以下情况下可转换为就绪态：①时间片用完被调度器抢占；②出现更高优先级进程进入就绪队列而被抢占（抢占式调度）。因此 D 错误。A、B、C 描述均正确。

**出处**：王道《操作系统》第二章 进程与线程

### 题 2

**题干**：（2020年408统考第23题）下列关于父进程与子进程的叙述中，错误的是

**选项**：
(A) 父进程与子进程共享虚拟地址空间
(B) 父进程与子进程可以并发执行
(C) 父进程与子进程的执行顺序由调度器决定
(D) 父进程与子进程各自拥有独立的进程控制块（PCB）

**标准答案**：$\boxed{A}$

**答案解析**：子进程被创建（如 fork）后拥有自己独立的虚拟地址空间（写时复制，COW），并不与父进程共享地址空间。父子进程可以并发执行，调度器决定其执行顺序，各自拥有独立的 PCB。因此 B、C、D 正确，A 错误。

**出处**：2020年全国硕士研究生招生考试计算机学科专业基础综合试题第23题

### 题 3

**题干**：在操作系统中，引入线程的主要目的是

**选项**：
(A) 减少进程调度的开销，提高程序并发度
(B) 提高CPU的运算速度
(C) 替代进程作为资源分配的基本单位
(D) 减少程序间的通信开销

**标准答案**：$\boxed{A}$

**答案解析**：线程是CPU调度的基本单位，它把"进程"的两大属性——"资源分配单位"和"调度执行单位"——解耦。同一进程内的线程共享地址空间和资源，线程切换只需保存少量寄存器上下文，开销远小于进程切换。这使得高并发任务（如Web服务器）可以轻量地创建和切换执行流。进程仍然是资源分配的基本单位。

**出处**：王道《操作系统》第二章

### 题 4

**题干**：（2017年408统考第23题）下列关于调度的叙述中，错误的是

**选项**：
(A) 作业调度是高级调度，决定把哪些作业装入内存
(B) 进程调度是低级调度，决定把CPU分配给哪个进程
(C) 中级调度（交换调度）的目的是提高内存利用率和系统吞吐量
(D) 在单CPU系统中，任意时刻都有且只有一个进程处于运行态

**标准答案**：$\boxed{D}$

**答案解析**：在单CPU系统中，任一时刻最多有一个进程处于运行态，但可能所有进程都阻塞（都在等待I/O），此时CPU空闲，运行态进程数为 0。因此"有且只有一个"表述错误。A、B、C 正确：三级调度分别是作业调度（高级，从外存到内存就绪）、进程调度（低级，从就绪到CPU）、中级调度（交换，将阻塞进程换出到外存以腾出内存）。

**出处**：2017年全国硕士研究生招生考试计算机学科专业基础综合试题第23题

### 题 5

**题干**：下列调度算法中，可能导致饥饿现象的是

**选项**：
(A) 先来先服务（FCFS）
(B) 时间片轮转（RR）
(C) 非抢占式短作业优先（SJF）
(D) 先来先服务 + 时间片轮转混合

**标准答案**：$\boxed{C}$

**答案解析**：SJF 算法中，如果不断有短作业到达，长作业可能永远得不到调度机会，出现"饥饿"。FCFS 按到达顺序调度，先进先出，不会饥饿；RR 按时间片轮流调度，每个进程公平获得到CPU，也不会饥饿。解决 SJF 饥饿问题的常用方法是"老化"（aging）——随等待时间增长逐渐提高长作业优先级。

**出处**：王道《操作系统》第二章

### 题 6

**题干**：（2015年408统考第23题）系统正在运行 n 个进程，每个进程需要 1 个资源 R 才能完成。若系统当前有 m 个已分配的 R 和 r 个空闲的 R。下列哪种情况下系统一定不会发生死锁？

**选项**：
(A) m + r ≥ n
(B) r ≥ n
(C) m ≥ n − 1 且 r ≥ 1
(D) r ≥ 1

**标准答案**：$\boxed{B}$

**答案解析**：死锁发生的一个必要条件是循环等待。一个经典的判断：如果每个进程最多需要 1 个资源，那么只要空闲资源数 r ≥ n，每个进程都能立即分配到所需资源并完成，一定不会死锁。A 选项 m + r ≥ n 只是资源总数够用，但可能每个进程都持有 1 个资源且等待另 1 个（本题每进程只需 1 个，故 A 实际也能成立，需看模型）。严格地，当"每进程仅需 1 个"时 r ≥ n 足以保证无死锁。

**出处**：2015年全国硕士研究生招生考试计算机学科专业基础综合试题第23题（改编）

### 题 7

**题干**：在信号量机制中，P 操作（wait）和 V 操作（signal）的作用是

**选项**：
(A) P操作申请资源，V操作释放资源
(B) P操作释放资源，V操作申请资源
(C) P操作和V操作都用于申请资源
(D) P操作和V操作都用于释放资源

**标准答案**：$\boxed{A}$

**答案解析**：Dijkstra 提出的信号量机制中，P 操作（Proberen，尝试）对信号量做减 1 操作，若结果为负则进程阻塞等待，等价于"申请一个资源"。V 操作（Verhogen，增加）对信号量做加 1 操作，若加 1 后信号量仍 ≤ 0，说明有进程在等待，需要唤醒一个等待进程，等价于"释放一个资源"。

**出处**：王道《操作系统》第二章

### 题 8

**题干**：（2014年408统考第23题）某系统中有 n 个进程共享 m 台同类资源，每台资源一次只能被一个进程使用。假设每个进程对资源的最大需求数为 w，则下列哪种情况系统可能死锁？

**选项**：
(A) m = 4, n = 3, w = 2
(B) m = 5, n = 4, w = 2
(C) m = 4, n = 3, w = 3
(D) m = 5, n = 5, w = 2

**标准答案**：$\boxed{C}$

**答案解析**：判断是否可能死锁的一个充分条件是：若 n(w−1) + 1 > m，则可能发生死锁（即每个进程已持有 w−1 个资源都还需要 1 个，但系统已无可分配资源，形成循环等待）。对 C 选项：3×(3−1)+1 = 7 > 4，可能死锁。对 A：3×1+1=4 ≤ 4；B：4×1+1=5 ≤ 5；D：5×1+1=6 > 5，但 w=2 时实际是需要 2 个资源，每个进程 1 个后还需 1 个，此时 5 进程各占 1 个共 5 个，空闲 0，需要 1 个，会死锁——需注意这里的判断。实际上经典判据 "n(w−1)+1 ≤ m 时不会死锁"。D：5×1+1=6 > 5，可能死锁。但 C 的情况更严重。标准答案按原始真题意图，C 正确。（需注意：该经典判断为"不会死锁"的充分条件是 n(w−1)+1 ≤ m，反之可能死锁。）

**出处**：2014年全国硕士研究生招生考试计算机学科专业基础综合试题第23题

### 题 9

**题干**：银行家算法是最著名的死锁避免算法。下列关于银行家算法的叙述中，正确的是

**选项**：
(A) 银行家算法通过破坏"占有并请求"条件来避免死锁
(B) 银行家算法每次都选择当前请求资源最少的进程先执行
(C) 银行家算法通过检测系统是否处于安全状态来决定是否分配资源
(D) 银行家算法要求进程在开始执行前必须申请全部所需资源

**标准答案**：$\boxed{C}$

**答案解析**：银行家算法是一种"死锁避免"算法，它在每次资源请求时模拟分配，检查是否能找到一个安全序列（即所有进程都能顺利完成的顺序），若能找到则分配，否则推迟分配。它并未破坏任何死锁必要条件，而是动态避免进入不安全状态。B 描述错误，安全序列检查不是简单地选资源最少的进程。D 是死锁预防（静态分配）的策略，不是银行家算法。

**出处**：王道《操作系统》第二章

### 题 10

**题干**：（2013年408统考第24题）下列关于死锁的说法中，错误的是

**选项**：
(A) 死锁产生的根本原因是系统资源不足和进程推进顺序不当
(B) 产生死锁的四个必要条件是：互斥、占有并请求、不剥夺、循环等待
(C) 破坏循环等待条件的方法之一是对资源进行有序编号
(D) 银行家算法属于死锁检测与解除的方法

**标准答案**：$\boxed{D}$

**答案解析**：银行家算法属于**死锁避免**，不是死锁检测与解除。死锁检测允许系统在运行中进入死锁状态，再通过检测算法（资源分配图化简）发现死锁并通过撤销进程或剥夺资源解除。A、B、C 均正确：对资源有序编号（层次分配）破坏了循环等待条件。

**出处**：2013年全国硕士研究生招生考试计算机学科专业基础综合试题第24题

### 题 11

**题干**：在一个单处理机系统中，若有 5 个用户进程，且用户进程均为CPU型进程（无I/O阻塞），则处于就绪状态的用户进程数最少为

**选项**：
(A) 0
(B) 1
(C) 4
(D) 5

**标准答案**：$\boxed{A}$

**答案解析**：一个CPU上任一时刻最多有一个进程运行。若所有 5 个进程都不阻塞，则最少有 4 个进程处于就绪状态，1 个运行。但题目问"最少为多少"，且未说所有进程都就绪——若每个进程都可能因等待I/O而阻塞（本题虽说是CPU型，但调度器切换时当前进程时间片用完后进入就绪，下一个从就绪中选）。严格地：若 CPU 型进程不阻塞，则就绪队列至少 4 个、运行 1 个，就绪数最少 4。但经典教材的标准答案为 0，这是因为"最少"可以是极端情况：全部进程阻塞。不过题目说"CPU型进程（无I/O阻塞）"，此时就绪数最少为 4，运行 1。这道题答案存在两种解读，建议以教材中对应题目为准。本题给出 C 作为更合理答案。

**出处**：王道《操作系统》第二章 经典习题

### 题 12

**题干**：下列选项中，不是进程控制块（PCB）中必须包含的信息是

**选项**：
(A) 进程标识符（PID）
(B) 进程状态
(C) CPU现场信息（寄存器值、PC等）
(D) 进程打开的文件描述符表
(E) 源程序代码

**标准答案**：$\boxed{E}$

**答案解析**：PCB 记录操作系统管理进程所需的全部信息，通常包括：PID、状态、优先级、CPU现场（PC、PSW、通用寄存器等）、内存管理信息（页表基址、段表、界限寄存器）、进程打开的文件表、I/O状态信息、记账信息、父子进程关系等。源程序代码属于进程的代码段/文本段，存储在进程的地址空间中，不放在 PCB 里。

**出处**：汤子瀛《计算机操作系统》第二章

### 题 13

**题干**：（2012年408统考第23题）下列选项中，导致创建新进程的操作是

Ⅰ. 用户登录成功　Ⅱ. 设备分配　Ⅲ. 启动程序执行　Ⅳ. 申请一块内存

**选项**：
(A) 仅Ⅰ和Ⅱ
(B) 仅Ⅱ和Ⅳ
(C) 仅Ⅰ和Ⅲ
(D) 仅Ⅰ、Ⅱ和Ⅲ

**标准答案**：$\boxed{C}$

**答案解析**：创建新进程的典型场景：①用户登录（如 login shell 创建子 shell）；②作业调度（启动批处理作业）；③用户启动程序执行（如 fork/exec）；④服务进程根据请求创建新进程（如 Web 服务器 fork 新进程处理请求）。设备分配（Ⅱ）只是把设备分配给已存在的进程；申请内存（Ⅳ）是当前进程的系统调用。因此仅Ⅰ和Ⅲ正确。

### 题 15

**题干**：下列关于优先级反转（Priority Inversion）的说法中，正确的是

**选项**：
(A) 优先级反转是高优先级进程抢占低优先级进程的正常现象
(B) 优先级反转指低优先级进程因持有高优先级进程需要的资源而间接阻塞高优先级进程，可能导致系统实时性失效
(C) 优先级反转只能在使用中断时发生
(D) 优先级反转问题无法解决

**标准答案**：$\boxed{B}$

**答案解析**：优先级反转是指：高优先级进程 H 需要某共享资源，但该资源正被低优先级进程 L 持有；而 L 可能又被中等优先级进程 M 抢占无法释放资源，结果 H 被 M 间接阻塞，高优先级形同虚设。经典解决方案包括"优先级继承"（L 继承 H 的优先级）和"优先级天花板协议"。A 描述的是正常抢占；C 不局限于中断；D 已有成熟解决方案。

**出处**：王道《操作系统》第二章

### 题 16

**题干**：（经典题）一个管程（monitor）不同于信号量的关键点是

**选项**：
(A) 管程每次可以让多个进程进入临界区
(B) 管程的互斥是由编译器在代码层面自动保证的，编程者无需显式调用P/V
(C) 管程不能实现条件同步
(D) 信号量比管程更高级

**标准答案**：$\boxed{B}$

**答案解析**：管程是一种高级同步原语，将共享数据和对它们的操作封装在一起，编译器在每个管程过程（procedure）前后自动插入互斥逻辑，保证任一时刻最多一个进程在管程内执行。管程内部通过条件变量（condition variable）实现条件同步（wait/signal 或 wait/broadcast）。因此 A、C 错误。D 语义反了，通常认为管程比信号量更抽象、更不易出错。

**出处**：汤子瀛《计算机操作系统》第二章

### 题 17

**题干**：某系统采用银行家算法进行资源分配。系统中有 5 个进程 P0~P4 和 3 类资源 A、B、C。T0 时刻的资源分配情况如下表所示（Available、Max、Allocation 均按 [A, B, C] 表示）：

| 进程 |   Max    | Allocation | Need = Max − Allocation |
| :--: | :------: | :--------: | :---------------------: |
|  P0  | [7, 5, 3] | [0, 1, 0]  |                           |
|  P1  | [3, 2, 2] | [2, 0, 0]  |                           |
|  P2  | [9, 0, 2] | [3, 0, 2]  |                           |
|  P3  | [2, 2, 2] | [2, 1, 1]  |                           |
|  P4  | [4, 3, 3] | [0, 0, 2]  |                           |

当前可用资源 Available = [3, 3, 2]。

请回答下列问题：

（1）求出每个进程的 Need 矩阵，并判断 T0 时刻系统是否处于安全状态。如果是，请给出一个安全序列。

（2）如果 T1 时刻进程 P1 发出资源请求 Request1 = [1, 0, 2]，系统能否满足该请求？请说明理由。

（3）如果在（2）的基础上，T2 时刻进程 P4 发出资源请求 Request4 = [3, 3, 0]，系统能否满足该请求？请说明理由。

**标准答案**：

（1）Need 矩阵：P0=[7,4,3]，P1=[1,2,2]，P2=[6,0,0]，P3=[0,1,1]，P4=[4,3,1]。系统安全，安全序列之一：<P1, P3, P4, P0, P2>。

（2）可以满足；分配后仍存在安全序列 <P1, P3, P4, P0, P2>。

（3）不能满足；P4 请求 [3,3,0] 超出当前可用资源，且 Need 检查后也无法分配。

**答案解析**：

**（1）计算 Need 矩阵**

Need = Max − Allocation：

- P0：[7,5,3] − [0,1,0] = [7, 4, 3]
- P1：[3,2,2] − [2,0,0] = [1, 2, 2]
- P2：[9,0,2] − [3,0,2] = [6, 0, 0]
- P3：[2,2,2] − [2,1,1] = [0, 1, 1]
- P4：[4,3,3] − [0,0,2] = [4, 3, 1]

初始 Available = [3, 3, 2]。

**安全检查（模拟分配）**：

- Work = [3, 3, 2]，Finish = [F, F, F, F, F]
- 寻找 Need ≤ Work 的进程：P1([1,2,2])、P3([0,1,1]) 满足。选 P1。
  - Work += Allocation(P1) = [3,3,2]+[2,0,0] = [5, 3, 2]，Finish(P1)=T。
- 继续寻找：P3([0,1,1])、P4([4,3,1]) 满足。选 P3。
  - Work += [2,1,1] = [7, 4, 3]，Finish(P3)=T。
- 继续寻找：P4([4,3,1])、P0([7,4,3]) 均满足。选 P4。
  - Work += [0,0,2] = [7, 4, 5]，Finish(P4)=T。
- 继续：P0([7,4,3]) 满足。选 P0。
  - Work += [0,1,0] = [7, 5, 5]，Finish(P0)=T。
- 继续：P2([6,0,0]) 满足。选 P2。
  - Work += [3,0,2] = [10, 5, 7]，Finish(P2)=T。

Finish 全为真，系统安全。**安全序列：<P1, P3, P4, P0, P2>**。（其他序列如 <P3, P1, ...> 也可能合法，只要每步都选到满足条件的进程即可。）

**（2）P1 请求 Request1 = [1, 0, 2]**

银行家算法三步检查：

① **Request ≤ Need**：[1,0,2] ≤ Need(P1)=[1,2,2] ✓

② **Request ≤ Available**：[1,0,2] ≤ Available=[3,3,2] ✓

③ **模拟分配并检查安全性**：

- Available 变为：[3,3,2] − [1,0,2] = [2, 3, 0]
- Allocation(P1) 变为：[2,0,0] + [1,0,2] = [3, 0, 2]
- Need(P1) 变为：[1,2,2] − [1,0,2] = [0, 2, 0]

新的资源状态：

| 进程 | Allocation | Need | Available |
| :--: | :--------: | :--: | :-------: |
| P0 | [0,1,0] | [7,4,3] | |
| P1 | [3,0,2] | [0,2,0] | |
| P2 | [3,0,2] | [6,0,0] | |
| P3 | [2,1,1] | [0,1,1] | [2,3,0] |
| P4 | [0,0,2] | [4,3,1] | |

**安全性检查**：Work = [2,3,0]。

- P1 Need=[0,2,0] ≤ [2,3,0] ✓。Work += [3,0,2] = [5,3,2]
- P3 Need=[0,1,1] ≤ [5,3,2] ✓。Work += [2,1,1] = [7,4,3]
- P4 Need=[4,3,1] ≤ [7,4,3] ✓。Work += [0,0,2] = [7,4,5]
- P0 Need=[7,4,3] ≤ [7,4,5] ✓。Work += [0,1,0] = [7,5,5]
- P2 Need=[6,0,0] ≤ [7,5,5] ✓。Work += [3,0,2] = [10,5,7]

存在安全序列 <P1, P3, P4, P0, P2>。因此**可以分配**。

**（3）P4 请求 Request4 = [3, 3, 0]**

此时 Available = [2, 3, 0]。

① **Request ≤ Need(P4)**：[3,3,0] ≤ [4,3,1] ✓（4≥3, 3≥3, 1≥0）

② **Request ≤ Available**：[3,3,0] ≤ [2,3,0]？ 3 ≤ 2 不成立 ✗

Request 超过了当前可用资源，进程 P4 必须阻塞等待。因此**系统不能立即满足该请求**。

（若进一步考虑 P4 是否"可被满足"——即使满足 Request4=[3,3,0]，则 Available 变为负数，无法运行任何其他进程；即使其他进程完成释放资源，P4 剩余 Need=[1,0,1] 也可以被后续满足，但算法的第二关已经拦住了本次请求。）

**出处**：王道《操作系统》第二章 银行家算法经典习题

### 题 18

**题干**：哲学家进餐问题是经典的进程同步问题。设有 5 个哲学家共用一张圆桌，分别坐在 5 张椅子上，桌中央有一碗无限的面条，5 人之间有 5 支筷子。哲学家的生活方式是交替地思考和进餐。每个哲学家想进餐时，总是试图分别拿起其左边和右边的筷子（先拿左、后拿右），只有拿到两支筷子后才能进餐；进餐完毕后放下两支筷子继续思考。

（1）请用信号量机制（P/V 操作）给出一种简单但可能出现死锁的解法，并说明为什么会死锁。

（2）请给出至少一种避免死锁的改进方案，并写出对应的伪代码。说明你的方案破坏了死锁的哪个必要条件。

（3）请用管程（monitor）+ 条件变量（condition variable）给出一种解决方案。

**标准答案**：

（1）给每支筷子设一个初值为 1 的信号量，哲学家拿左筷 P(left) 再拿右筷 P(right)。若 5 个哲学家同时拿起左筷后都阻塞等待右筷，出现循环等待，死锁。

（2）方案举例：①最多只允许 4 个哲学家同时进餐（破坏占有并请求/循环等待）；②奇数号先拿左筷再拿右筷，偶数号相反（破坏循环等待）；③原子地同时拿两支筷子（破坏占有并请求）。

（3）管程内封装状态变量和条件变量，用 pick_up(i) 和 put_down(i) 两个过程。

**答案解析**：

**（1）可能死锁的简单方案**

```
semaphore chopstick[5] = {1, 1, 1, 1, 1};  // 5 支筷子

philosopher(int i) {
    while (true) {
        think();
        P(chopstick[i]);              // 拿左筷（第 i 支）
        P(chopstick[(i+1) % 5]);      // 拿右筷（第 i+1 支）
        eat();
        V(chopstick[i]);              // 放左筷
        V(chopstick[(i+1) % 5]);      // 放右筷
    }
}
```

**死锁成因**：若 5 个哲学家几乎同时想进餐，每个都先执行 `P(chopstick[i])` 成功拿到左筷，然后在 `P(chopstick[i+1])` 上等待右筷。此时：

- 互斥条件满足（每支筷子同一时刻只能被一个人持有）；
- 占有并请求条件满足（每个人都已持有一支筷子并请求另一支）；
- 不剥夺条件满足（没有人主动放下）；
- 循环等待条件满足（P0 等 P1 右筷 → P1 等 P2 右筷 → … → P4 等 P0 右筷 → P0）。

四个必要条件同时满足，死锁发生。

**（2）避免死锁的改进方案**

**方案 A：最多允许 4 个哲学家同时进入餐厅**

```
semaphore chopstick[5] = {1, 1, 1, 1, 1};
semaphore eaters = 4;            // 最多 4 人同时进餐

philosopher(int i) {
    while (true) {
        think();
        P(eaters);               // 申请进入餐厅
        P(chopstick[i]);
        P(chopstick[(i+1) % 5]);
        eat();
        V(chopstick[i]);
        V(chopstick[(i+1) % 5]);
        V(eaters);               // 离开餐厅
    }
}
```

**原理**：最多 4 个竞争者争 5 支筷子，根据鸽巢原理至少有 1 个哲学家能拿到两支筷子顺利吃完并释放，从而打破循环等待。破坏了"循环等待"条件（也部分限制了"占有并请求"）。

**方案 B：对哲学家编号，奇数号先拿左筷，偶数号先拿右筷**

```
semaphore chopstick[5] = {1, 1, 1, 1, 1};

philosopher(int i) {
    while (true) {
        think();
        if (i % 2 == 1) {              // 奇数号：先左后右
            P(chopstick[i]);
            P(chopstick[(i+1) % 5]);
        } else {                        // 偶数号：先右后左
            P(chopstick[(i+1) % 5]);
            P(chopstick[i]);
        }
        eat();
        V(chopstick[i]);
        V(chopstick[(i+1) % 5]);
    }
}
```

**原理**：对资源请求顺序做全局排序（相当于对筷子层次编号），破坏了"循环等待"条件。想象编号 0,1,2,3,4 顺时针排列：0 先拿右筷（编号 1）再拿左筷（编号 0），与 1 先拿 1 再拿 2 的顺序配合，消除循环。

**方案 C：原子地同时拿起两支筷子**

```
semaphore chopstick[5] = {1, 1, 1, 1, 1};
semaphore mutex = 1;                 // 保护拿筷操作的原子性

philosopher(int i) {
    while (true) {
        think();
        P(mutex);                    // 进入临界区：一人拿筷
        P(chopstick[i]);
        P(chopstick[(i+1) % 5]);
        V(mutex);                    // 出临界区
        eat();
        V(chopstick[i]);
        V(chopstick[(i+1) % 5]);
    }
}
```

**原理**：任一时刻只有一个哲学家在拿筷子，拿到两支后才释放临界区，其他人才开始。这破坏了"占有并请求"条件（拿到左筷时别人不会再去拿右筷后阻塞）。代价是并发度低，任一时刻最多 1 人进餐。

**（3）管程（Monitor）方案**

```
monitor DiningPhilosophers {
    enum State { THINKING, HUNGRY, EATING };
    State state[5];
    condition self[5];            // self[i]: 哲学家 i 的条件变量

    void pick_up(int i) {
        state[i] = HUNGRY;
        test(i);                  // 尝试拿筷
        if (state[i] != EATING)
            self[i].wait();       // 拿不到则阻塞
    }

    void put_down(int i) {
        state[i] = THINKING;
        test((i + 4) % 5);        // 通知左邻
        test((i + 1) % 5);        // 通知右邻
    }

    void test(int k) {
        if (state[(k + 4) % 5] != EATING &&
            state[k] == HUNGRY &&
            state[(k + 1) % 5] != EATING) {
            state[k] = EATING;
            self[k].signal();     // 唤醒该哲学家
        }
    }
}

// 哲学家进程（在管程之外调用）
philosopher(int i) {
    while (true) {
        think();
        DiningPhilosophers.pick_up(i);
        eat();
        DiningPhilosophers.put_down(i);
    }
}
```

**原理**：管程保证同一时刻只有一个进程在 pick_up / put_down / test 中执行（互斥由编译器保证）。test(k) 检查左邻右舍是否都不在进餐。若哲学家 i 在 pick_up 中未能成功变为 EATING，则在 self[i] 上等待；当邻居放筷时会通过 test(i) 重新检查并唤醒 i。此方案避免忙等、避免死锁，且允许多人同时进餐（最多 2 人）。

**出处**：Dijkstra 1965 年提出的经典问题；汤子瀛《计算机操作系统》、王道《操作系统》第二章同步与互斥

### 题 19

**题干**：设有两个进程 P 和 Q，它们共享一个变量 x。P 的代码是 "x = x + 1;"，Q 的代码是 "x = x − 1;"。假设 x 的初值为 0。每个进程各执行一次。请回答：

（1）在没有任何同步保护的情况下，x 最终的可能取值有哪些？请举例说明对应的执行序列。

（2）这一现象叫什么？其发生的三个必要条件是什么？

（3）请使用信号量给出一种正确的同步方案，使 x 的最终值恒为 0。

（4）请使用 TestAndSet 硬件指令（原子交换）给出另一种正确方案。

**标准答案**：

（1）可能值：−1, 0, 1。取决于两条高级语言指令被打断的方式。
（2）竞态条件（race condition）。必要条件：①存在共享数据；②进程以非原子方式访问；③执行顺序不可预测。
（3）设信号量 mutex=1，P、Q 均执行 P(mutex); x=... ; V(mutex)。
（4）使用锁变量 lock 初值为 false，进入临界区前 while(TestAndSet(&lock)) ; 退出时 lock = false。

**答案解析**：

**（1）x 的可能取值分析**

高级语言语句 "x = x + 1" 在机器层面通常分解为三条指令（示意）：
```
LOAD  R1, x       // 取 x 到寄存器
ADD   R1, R1, #1  // 寄存器 +1
STORE x,  R1      // 写回
```
同理 "x = x − 1"：
```
LOAD  R2, x
SUB   R2, R2, #1
STORE x,  R2
```

设 P 执行 `x=x+1`，Q 执行 `x=x-1`，初值 x=0。

**情况①串行执行 P→Q**：P 完整执行 x 变为 1，Q 完整执行 x 变为 0。**结果 0**。

**情况②串行执行 Q→P**：Q 执行后 x=−1，P 执行后 x=0。**结果 0**。

**情况③P 的 LOAD 之后被 Q 打断**：P 已读 x=0，但还没写回；Q 完整执行读 x=0、减 1、写回 x=−1；P 恢复后把自己寄存器里的 1 写回，覆盖成 1。**结果 1**。

**情况④Q 的 LOAD 之后被 P 打断**：Q 已读 x=0；P 完整执行后 x=1；Q 恢复把自己寄存器里的 −1 写回，覆盖成 −1。**结果 −1**。

结论：**x 可能为 −1, 0, 1**，且 1 和 −1 都违反了直觉上 "+1 再 −1 得 0" 的预期。

**（2）竞态条件（Race Condition）**

多个进程并发访问和操作共享数据，且执行结果依赖于进程的相对执行顺序，这种现象称为**竞态条件**。发生的三个必要条件：

1. **存在共享的可写数据**（不是只读数据）；
2. **对共享数据的访问不是原子的**（即可以被打断，且操作不是单条不可中断指令完成）；
3. **执行顺序不可预测**（调度器的选择不可由程序员假定）。

解决思路：将对共享数据的操作包裹为**临界区**，并通过互斥保证任一时刻最多一个进程在临界区内执行。

**（3）信号量方案**

```
int x = 0;
semaphore mutex = 1;         // 互斥信号量

process P() {
    P(mutex);                // 进入临界区
    x = x + 1;               // 临界区操作
    V(mutex);                // 退出临界区
}

process Q() {
    P(mutex);
    x = x - 1;
    V(mutex);
}
```

`mutex` 初值为 1，任一时刻最多一个进程成功进入临界区。P 操作申请互斥权（若 mutex=0 则阻塞），V 操作释放互斥权并唤醒等待者。注意必须保证 P/V 操作本身是原子原语（由操作系统内核或关中断实现）。最终结果恒为 0。

**（4）TestAndSet 硬件指令方案**

`TestAndSet(&lock)` 是一条硬件原子指令：原子地将 lock 的旧值返回并把 lock 设为 true。利用它实现忙等锁（spinlock）：

```
int x = 0;
bool lock = false;          // 锁变量，false 表示空闲

process P() {
    while (TestAndSet(&lock)) ;  // 原子地申请锁；若已持有则忙等
    x = x + 1;                   // 临界区
    lock = false;                // 释放锁
}

process Q() {
    while (TestAndSet(&lock)) ;
    x = x - 1;
    lock = false;
}
```

**正确性论证**：TestAndSet 的原子性保证即便多个进程同时执行，也只有一个会看到 lock=false 并获得锁，其他进入 while 循环忙等。退出临界区时 lock=false 释放锁。没有信号量时也能实现互斥，但该方案是忙等的，CPU 利用率不高；若调度器不可抢占，忙等还可能导致死锁（但对抢占式调度器可用）。最终结果恒为 0。

**出处**：汤子瀛《计算机操作系统》第二章；王道《操作系统》第二章 临界区问题

### 题 20

**题干**：在生产者−消费者问题中，有 n 个缓冲区构成一个环形队列，每个缓冲区可放一个产品。生产者进程每次生产一个产品放入缓冲区，消费者进程每次从缓冲区取出一个产品使用。设生产者和消费者各有若干个。请回答：

（1）该问题需要几个信号量？分别说明其含义、初值以及作用。

（2）写出使用 P/V 操作的生产者和消费者伪代码。

（3）在你的解答中，若把生产者进程中两个 P 操作的顺序颠倒会发生什么问题？说明原因。

（4）若缓冲区为空，此时调度器先调度到消费者，试跟踪说明信号量机制如何让消费者等待、以及之后生产者如何唤醒消费者。

**标准答案**：

（1）3 个信号量：mutex(=1) 保护缓冲区的互斥访问；empty(=n) 空缓冲区数量；full(=0) 满缓冲区数量。
（2）生产者：P(empty)→P(mutex)→生产→V(mutex)→V(full)；消费者：P(full)→P(mutex)→消费→V(mutex)→V(empty)。
（3）若颠倒为 P(mutex)→P(empty)，则可能死锁：消费者先占 mutex 后因 full=0 阻塞，生产者因 mutex=0 无法进入，双方互相等待。
（4）缓冲区空时 full=0，消费者 P(full) 阻塞；生产者 P(empty=n) 通过并生产后执行 V(full)，使 full 加 1 并唤醒消费者。

**答案解析**：

**（1）信号量设计**

- **mutex**：初值 1，作为临界区互斥锁。保护对环形队列（in、out 指针和 buffer 数组）的插入/取出操作。
- **empty**：初值 n，表示空缓冲区的数量（还可放多少个产品）。生产者在放产品前必须 P(empty) 申请空槽。
- **full**：初值 0，表示满缓冲区的数量（已有多少产品）。消费者在取产品前必须 P(full) 申请产品槽。

其中，empty 和 full 还起到资源计数和条件同步的双重作用：它们把"缓冲区满/空"的同步语义编码进信号量值中。

**（2）生产者/消费者伪代码**

```
int buffer[n];                 // 环形缓冲区
int in = 0, out = 0;           // 生产位置、消费位置

semaphore mutex = 1;
semaphore empty = n;
semaphore full  = 0;

producer() {
    while (true) {
        item = produce_item();         // 生产一个产品
        P(empty);                      // 申请空缓冲区
        P(mutex);                      // 进入临界区
        buffer[in] = item;             // 放入缓冲区
        in = (in + 1) % n;             // 更新生产指针
        V(mutex);                      // 退出临界区
        V(full);                       // 满缓冲区 +1，可能唤醒消费者
    }
}

consumer() {
    while (true) {
        P(full);                       // 申请一个满缓冲区
        P(mutex);                      // 进入临界区
        item = buffer[out];            // 取出产品
        out = (out + 1) % n;           // 更新消费指针
        V(mutex);                      // 退出临界区
        V(empty);                      // 空缓冲区 +1，可能唤醒生产者
        consume_item(item);            // 使用产品
    }
}
```

**（3）P 操作顺序颠倒导致死锁**

若将生产者改为：
```
P(mutex);       // 先拿锁
P(empty);       // 再申请空槽
...
V(mutex); V(full);
```
同理消费者改为：
```
P(mutex);       // 先拿锁
P(full);        // 再申请满槽
...
V(mutex); V(empty);
```

**死锁场景**：假设缓冲区全满（empty=0, full=n）。调度器先调度消费者：消费者 P(mutex) 成功拿到锁，然后 P(full) 成功取走一个产品变为 full=n−1，没问题。反复多次直到缓冲区为空。

更典型的场景：假设缓冲区已满，调度器选择调度一个生产者。生产者 P(mutex) 成功拿到锁后执行 P(empty)，但 empty=0，生产者阻塞在 empty 上——但它已持有 mutex。之后任何消费者想进入都在 P(mutex) 上阻塞，无法消费、无法释放 empty。生产者等待 empty、消费者等待 mutex，**循环等待形成死锁**。

**教训**：P 操作中，"资源信号量"（empty、full）必须在"互斥信号量"（mutex）之前申请；V 操作顺序可互换（但一般先释放 mutex 以减少临界区长度）。

**（4）缓冲区为空时的信号量交互跟踪**

设缓冲区初态：empty=n, full=0, mutex=1, in=out=0。

1. 调度器先调度消费者 C：
   - C 执行 `P(full)`：full 原值 0 → 减 1 后为 −1。根据 P 操作语义（"若 s<0 则阻塞"），C 被加入 full 的等待队列，让出 CPU。此时 full = −1（其绝对值表示等待进程数，一种常见实现）。

2. 调度器调度生产者 P：
   - P 执行 `P(empty)`：empty=n → n−1。n−1 ≥ 0，继续。
   - P 执行 `P(mutex)`：mutex=1 → 0。进入临界区。
   - P 把产品 item 放入 buffer[in]，in 前移。
   - P 执行 `V(mutex)`：mutex=0 → 1。
   - P 执行 `V(full)`：full=−1 → 加 1 后为 0。根据 V 操作语义（"若 s≤0 说明有进程等待，唤醒一个"），从 full 的等待队列中唤醒消费者 C。C 变为就绪态。

3. C 被调度恢复执行时，从 P(full) 的"阻塞返回点"继续，相当于成功通过了 P 操作。接下来执行 `P(mutex)` → 取产品 → `V(mutex)` → `V(empty)` → 消费。

最终一个产品从生产者流转到消费者，信号量恢复为 empty=n−1, full=0（初始态的"空"状态在一次成功生产+消费后仍保持"空"；但若只有一次生产没消费，则 full=1，empty=n−1）。

**出处**：Dijkstra 1965 年提出的经典合作进程问题；汤子瀛《计算机操作系统》、王道《操作系统》第二章

### 题 21

**题干**：读者写者问题是另一类经典同步问题。某数据库被多个进程共享，其中一些进程只需要读（读者），另一些需要写（写者）。允许多个读者同时读，但任一时刻只能有一个写者写，且写者写时不允许任何读者读。请回答：

（1）第一类读者写者问题（读者优先）的要求是什么？使用信号量给出其解法伪代码，并说明为什么"读者优先"。

（2）第二类读者写者问题（写者优先）的要求是什么？与读者优先相比，需要增加什么信号量/机制？简述方案思路。

（3）在（1）的方案中，说明写者可能遇到的问题。若系统不断有新读者到来，写者会怎样？这又叫什么现象？如何缓解？

**标准答案**：

（1）读者优先：一旦有读者在读，后续读者可以直接进入而无需等待写者；写者必须等所有读者离开。使用 rmutex(=1) 保护 readcount，wmutex(=1) 保护写操作。第一个进入的读者 P(wmutex) 抢写者锁，最后离开的读者 V(wmutex) 释放。

（2）写者优先：一旦有写者等待，新到达的读者必须等待该写者完成。需要额外信号量（如 r=1 或读写锁的"写等待"逻辑）让后续读者在写者已申请的情况下被阻塞。

（3）写者可能饥饿（starvation）：若读者持续到达，写者永远等不到 wmutex 被释放。可通过老化、公平队列等机制缓解；或使用写者优先策略。

**答案解析**：

**（1）第一类读者写者问题（读者优先 / Readers-Preference）**

**要求**：多个读者可同时读；写操作与任何其他操作（读/写）互斥；且"一旦有读者正在读，新读者可以直接进入读而不必等待写者"。

**信号量设计**：

- **wmutex**：初值 1。写者之间互斥，也用于读者与写者互斥（第一个读者进入时占有它，最后一个读者离开时释放它）。
- **rmutex**：初值 1。保护对共享计数器 `readcount` 的访问。
- **readcount**：初值 0。记录当前正在读的读者数量。

**伪代码**：

```
semaphore wmutex = 1;         // 写者互斥锁（写者之间、第一个读者与写者互斥）
semaphore rmutex = 1;         // 保护 readcount
int readcount = 0;

reader() {
    while (true) {
        P(rmutex);
        readcount = readcount + 1;
        if (readcount == 1)
            P(wmutex);         // 第一个读者锁上写者入口
        V(rmutex);

        /* 临界区：读数据 */

        P(rmutex);
        readcount = readcount - 1;
        if (readcount == 0)
            V(wmutex);         // 最后一个读者释放写者入口
        V(rmutex);
    }
}

writer() {
    while (true) {
        P(wmutex);              // 申请写权限
        /* 临界区：写数据 */
        V(wmutex);
    }
}
```

**为什么"读者优先"**：当已有读者在读（readcount ≥ 1）时，wmutex 已被第一个读者持有。后续读者只需更新 readcount 而不需再竞争 wmutex——它们可直接进入读。此时若有写者请求，只能在 wmutex 上等待，直到所有读者都读完离开。读者可以"源源不断地插队"，写者被延后。

**（2）第二类读者写者问题（写者优先 / Writers-Preference）**

**要求**：一旦写者提出写请求，之后到达的所有读者都必须等这个写者完成（即使当前还有读者在读）。即：写者具有"插队优先"权。

**思路**：需要额外机制让"写者已声明意图"这个事实能阻塞新读者。典型做法是增加一个信号量 `r`（初值 1）作为"读请求的大门"：

- **写者**执行时先 P(r)（阻止后续读者申请），再 P(wmutex)（等待当前正在读/写的进程结束），写完释放 wmutex 再释放 r。
- **读者**在进入前也必须 P(r)（和写者公平竞争），然后再像读者优先方案里那样处理 readcount/wmutex，但注意 P(r) 的位置应在 P(rmutex) 外层。

示意伪代码：

```
semaphore wmutex = 1;          // 控制对数据库的写（读者的第一个/最后一个仍用它）
semaphore rmutex = 1;          // 保护 readcount
semaphore r = 1;               // 写者用它堵住新读者
int readcount = 0;

reader() {
    P(r);                      // 与写者公平抢"大门"
    P(rmutex);
    readcount++;
    if (readcount == 1) P(wmutex);
    V(rmutex);
    V(r);                      // 打开大门，允许后续读者/写者竞争
    /* 读 */
    P(rmutex);
    readcount--;
    if (readcount == 0) V(wmutex);
    V(rmutex);
}

writer() {
    P(r);                      // 关上大门，后续读者将被卡在 P(r)
    P(wmutex);                 // 等当前读者/写者完成
    /* 写 */
    V(wmutex);
    V(r);                      // 打开大门
}
```

**为什么这是写者优先**：写者只要成功 P(r)，所有后续到达的读者都会卡在 P(r) 上，无法再进入读。正在读的读者读完后释放 wmutex，写者即可开始写。在此期间新读者一律等待，写者得以优先。

**（3）读者优先下的写者饥饿问题**

在方案（1）中，如果**不断有新读者到达**，则 readcount 始终 ≥ 1，wmutex 永远不会被释放，写者将被无限期推迟。这就是**饥饿（Starvation）**。饥饿与死锁的区别：饥饿并非所有参与者都阻塞（读者一直在推进），而是某个或某些进程长期得不到服务。

**缓解方式**：

1. **写者优先策略**：如（2）所述，写者到来时堵住新读者。
2. **到达顺序排队（FIFO 调度）**：按请求到达顺序赋予服务权，先到先服务。写者在读者之后到达时等待这批读者完成，然后写者先执行；新读者在写者之后到就必须等待写者。
3. **老化（Aging）**：随等待时间增长动态提升写者的优先级。
4. **读写锁的"公平模式"**：现代操作系统提供的 pthread_rwlock 等机制通常支持写者优先或公平模式，可根据需要配置。

**出处**：Courtois, Heymans, Parnas (1971) "Concurrent Control with Readers and Writers"；汤子瀛《计算机操作系统》、王道《操作系统》第二章
