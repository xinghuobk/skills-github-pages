### 一、数据结构与算法（1-8）

**问题 1：什么是时间复杂度和空间复杂度？如何分析一个算法的复杂度？**

**答题要点**：
- 时间复杂度 O(f(n))：算法执行时间随问题规模 n 的增长率上界
- 空间复杂度 O(g(n))：算法所需存储空间随问题规模 n 的增长率上界
- 分析方法：
  1. 找出基本操作（循环体、递归调用）
  2. 分析基本操作的执行次数与 n 的关系
  3. 取最高次项，忽略常数系数
  4. 递归算法可用主定理 / 递推方程求解
- 常见复杂度排序：O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(n³) < O(2ⁿ) < O(n!)

**问题 2：比较线性表的顺序存储（数组）和链式存储（链表）的优缺点**

**答题要点**：

| 比较项目 | 顺序存储 | 链式存储 |
|---------|---------|---------|
| 存储方式 | 连续内存块 | 分散节点 + 指针 |
| 随机访问 | ✓ O(1) | ✗ O(n) 需遍历 |
| 插入/删除头部 | O(n) 需移动元素 | O(1) 仅修改指针 |
| 插入/删除中间/尾部 | O(n) | O(1)（已知位置）/ O(n)（需查找）|
| 空间开销 | 固定大小，可能浪费 | 每个节点需存储指针 |
| 存储密度 | =1（高效）| <1（指针有开销）|
| 扩容 | 需重新分配空间（realloc）| 按需分配，天然动态 |
| Cache 友好性 | ✓ 顺序访问命中率高 | ✗ 指针跳转破坏局部性 |

**应用场景**：
- 数组：元素数量稳定、需要随机访问、追求访问速度（如哈希表的桶、动态规划表）
- 链表：频繁插入删除、元素数量不确定（如 LRU Cache 的链表维护队列顺序）

**问题 3：什么是哈希表？如何解决哈希冲突？**

**答题要点**：

**哈希表（Hash Table）**：通过哈希函数 h(key) 将关键字映射到数组下标，实现 O(1) 平均查找时间的数据结构。

**冲突解决方法**：

1. **链地址法（Chaining / Separate Chaining）**：
   - 每个哈希桶挂一个链表（或红黑树，Java HashMap ≥8 时树化）
   - 冲突元素加入链表
   - 优点：简单，删除方便，不会产生二次聚集
   - 缺点：链表过长时退化为 O(n)，需要 rehash

2. **开放地址法（Open Addressing）**：
   - 探测序列 h(key), h(key)+1, h(key)+2... 找空槽
   - 线性探测：h(key) + i（可能产生"一次聚集"）
   - 二次探测：h(key) + i²（缓解一次聚集，但可能有"二次聚集"）
   - 双重散列：h₁(key) + i·h₂(key)（最佳，无聚集）
   - 优点：不用链表，存储密度高
   - 缺点：删除必须用"墓碑"(tombstone) 标记，不能物理删除

3. **再哈希法**：准备多个哈希函数，冲突时换一个

4. **建立公共溢出区**：冲突元素放入溢出表

**装填因子 α = n/m**（n=元素数, m=桶数），α 越大冲突越多，一般取 0.7 左右触发扩容。

**问题 4：描述二叉树的三种非递归遍历方式**

**答题要点**：

**前序遍历（根-左-右）**：
```
栈 stack; p = root;
while (p || !stack.empty()) {
    while (p) {
        visit(p);           // 访问
        push(p);            // 入栈保存
        p = p->left;        // 深入左子树
    }
    p = stack.top(); stack.pop();
    p = p->right;           // 转向右子树
}
```

**中序遍历（左-根-右）**：
```
栈 stack; p = root;
while (p || !stack.empty()) {
    while (p) {
        push(p);
        p = p->left;
    }
    p = stack.top(); stack.pop();
    visit(p);               // 出栈时访问
    p = p->right;
}
```

**后序遍历（左-右-根）**：需要标记节点是第几次出栈
```
栈 stack; p = root; prev = null;
while (p || !stack.empty()) {
    while (p) {
        push(p);
        p = p->left;
    }
    p = stack.top();
    if (!p->right || p->right == prev) {
        visit(p);           // 右子树已访问过，现在访问根
        stack.pop();
        prev = p;
        p = null;
    } else {
        p = p->right;       // 否则先处理右子树
    }
}
```

**Morris 遍历**：利用叶子节点的右指针指向中序后继，实现 O(1) 空间遍历。

**问题 5：描述并查集（Disjoint Set Union, DSU）的实现和应用**

**答题要点**：

**数据结构**：维护一个不相交集合的集合，支持两个操作：
- `find(x)`：查找 x 所在集合的代表元
- `union(x, y)`：合并 x 和 y 所在的集合

**核心优化**：

1. **路径压缩（Path Compression）**：find 时将路径上的节点直接指向根
```
int find(int x) {
    return parent[x] == x ? x : (parent[x] = find(parent[x]));
}
```

2. **按秩合并（Union by Rank / Size）**：将小树挂到大树下
```
void union(int x, int y) {
    x = find(x), y = find(y);
    if (x == y) return;
    if (rank[x] < rank[y]) swap(x, y);
    parent[y] = x;
    if (rank[x] == rank[y]) rank[x]++;
}
```

**时间复杂度**：几乎常数时间，精确为 α(n)（反阿克曼函数），对任何实际 n ≤ 5

**经典应用**：
- 最小生成树（Kruskal 算法：按边权排序后用并查集避免成环）
- 亲戚问题 / 朋友圈（LeetCode 547: Friend Circles）
- 图的连通分量计数
- 等价类问题（如判断等式方程组是否可满足）
- 岛屿数量的动态合并

**问题 6：比较快速排序和归并排序，说明它们的优缺点和适用场景**

**答题要点**：

| 特性 | 快速排序 (QuickSort) | 归并排序 (MergeSort) |
|-----|---------------------|---------------------|
| 平均时间 | O(n log n) | O(n log n) |
| 最坏时间 | O(n²)（已排序 + 选首元素为 pivot） | O(n log n) |
| 空间复杂度 | O(log n)（递归栈） | O(n)（额外数组） |
| 稳定性 | 不稳定（相同元素可能交换位置） | 稳定 |
| 原地排序 | ✓ | ✗ |
| Cache 友好 | ✓（顺序访问小数组） | ✗（频繁跨数组访问） |
| 小数据表现 | 极好（可配合 insertion sort） | 常数因子较大 |

**快排优化策略**：
1. **三数取中**：选首、中、尾的中位数作为 pivot，避免最坏情况
2. **随机化**：随机选 pivot，将最坏情况变为概率事件
3. **三路划分（Dutch National Flag）**：将数组分为 <pivot, =pivot, >pivot 三部分，处理大量重复元素
4. **尾递归优化 / 迭代实现**：避免栈溢出
5. **小数组切换到插入排序**：n < 10~20 时插入排序更快

**适用场景**：
- 快排：大多数通用排序（C++ std::sort 的主体）
- 归并排序：需要稳定性（如 Java Arrays.sort 对对象类型）、链表排序、外部排序（磁盘数据太大不能全载入内存）

**问题 7：什么是动态规划？说明其核心思想和解题步骤，并举一例**

**答题要点**：

**动态规划（DP, Dynamic Programming）**：将复杂问题分解为子问题，通过保存子问题的解避免重复计算。

**适用条件**：
1. **最优子结构**：问题的最优解包含子问题的最优解
2. **重叠子问题**：子问题在求解中会被重复计算（否则用分治即可）

**核心思想**：
- **记忆化搜索（Top-down）**：递归 + 缓存已计算结果
- **递推（Bottom-up）**：从最简单子问题开始迭代计算

**解题步骤**（DP 五步法）：
1. **定义状态**：明确 dp[i] 或 dp[i][j] 表示什么
2. **写出状态转移方程**：找出 dp[i] 与 dp[i-1]、dp[i-2] 等的关系
3. **初始化**：确定边界条件（如 dp[0], dp[1]）
4. **确定计算顺序**：确保计算 dp[i] 时所需的子问题已解出
5. **考虑优化空间**：若只依赖前 1~2 个状态，可用滚动数组降低空间

**举例：最长递增子序列 (LIS)**：
- 状态：dp[i] = 以 nums[i] 结尾的 LIS 长度
- 方程：dp[i] = max(dp[j]) + 1，其中 j < i 且 nums[j] < nums[i]
- 初始化：dp[i] = 1（每个元素自身）
- 答案：max(dp)
- 优化：贪心 + 二分查找 O(n log n)

**常见 DP 类型**：
- 线性 DP（LIS, 打家劫舍）
- 区间 DP（矩阵连乘, 石子合并）
- 背包 DP（0/1 背包, 完全背包, 多重背包）
- 树形 DP（树的最大独立集）
- 状态压缩 DP（旅行商问题 TSP）
- 数位 DP（计数满足条件的数字）

**问题 8：什么是图的最小生成树（MST）？比较 Prim 算法和 Kruskal 算法**

**答题要点**：

**最小生成树**：无向连通带权图中，包含所有顶点且边权和最小的生成树（n-1 条边，无环）。

**性质**：
- **割性质**：将顶点分为 S 和 V-S，跨割的最小权边必在某个 MST 中
- **圈性质**：环中的最大权边不在 MST 中
- **唯一性**：所有权互不相同 ⇒ MST 唯一

**Kruskal 算法**（避圈法，从边的角度）：
```
按权从小到大排序所有边
初始化并查集（每个顶点独立集合）
依次遍历每条边 (u, v, w):
    if find(u) != find(v):      // u, v 不在同一集合
        将边加入 MST
        union(u, v)
时间：O(E log E)    空间：O(E)
```

**Prim 算法**（从顶点的角度）：
```
从任意顶点 s 开始，维护已选集合 S
维护数组 key[v] = v 到 S 的最小边权
重复 n-1 次:
    选 V-S 中 key 最小的顶点 u
    将 u 加入 S
    更新 u 的邻居 v: key[v] = min(key[v], weight(u, v))
用堆实现: O(E log V)    用邻接矩阵: O(V²)
```

**对比**：

| 项目 | Kruskal | Prim |
|-----|---------|------|
| 思路 | 选边（全局最小合法边） | 选点（从已选集合扩展） |
| 数据结构 | 并查集 + 排序 | 最小堆 / 优先队列 |
| 时间复杂度 | O(E log E) | O(E log V) 堆优化 / O(V²) 矩阵 |
| 适用图 | 稀疏图（E 小） | 稠密图（E ≈ V²） |
| 多连通分量 | 自动处理（可得到最小生成森林） | 需要对每个分量运行 |
| 实现复杂度 | 简单 | 稍复杂（堆操作需要维护）|

### 二、计算机组成原理（9-14）

**问题 9：什么是 Cache？说明 Cache 的工作原理和替换策略**

**答题要点**：

**Cache（高速缓存）**：CPU 和主存之间的小容量高速存储器，利用程序的**局部性原理**（时间局部性：刚访问的数据可能再访问；空间局部性：附近的数据可能被访问）来减少对慢速主存的访问。

**工作原理**：
1. **命中**：CPU 访问的数据在 Cache 中 → 直接从 Cache 读取（几 ns）
2. **失效**：数据不在 Cache 中 → 从主存读取（几十~几百 ns），同时将包含该数据的块调入 Cache

**地址映射方式**：

1. **直接映射**（Direct Mapped）：
   - cache_line = (address / block_size) % num_lines
   - 每个主存块只能映射到一个特定 Cache 行
   - 优点：简单、速度快
   - 缺点：冲突失效多（两个频繁使用的块映射到同一行）

2. **全相联**（Fully Associative）：
   - 主存块可以放在任意 Cache 行
   - 优点：冲突最少，命中率高
   - 缺点：需要并行比较所有 tag，硬件成本高（容量小、相联存储器贵）

3. **组相联**（Set-Associative）：
   - cache_set = (address / block_size) % num_sets
   - 每组有 N 路（N-way set associative），在组内全相联
   - 常见：2-way, 4-way, 8-way, 16-way
   - 平衡方案：直接映射的速度 + 全相联的命中率

**替换策略**（Cache 满时替换哪一行）：

1. **FIFO**：替换最早调入的行（简单，但可能替换"热"数据）
2. **LRU（Least Recently Used）**：替换最久未使用的行（理论最优近似，但硬件实现成本高，通常用伪 LRU）
3. **LFU（Least Frequently Used）**：替换使用次数最少的行
4. **随机替换**：随机选一行（硬件最简单，性能不错）

**写策略**（处理写操作）：
- **写通（Write-through）**：同时写 Cache 和主存（简单，一致性好，写延迟高）
- **写回（Write-back）**：只写 Cache，标记 dirty，替换时才写回主存（写性能好，一致性复杂）
- **写分配（Write-allocate）**：写失效时先将块调入 Cache 再写
- **非写分配**：写失效时直接写主存（不调入 Cache）

**问题 10：描述指令流水线的工作原理和冒险（Hazard）**

**答题要点**：

**指令流水线**：将一条指令的执行分解为多个阶段（经典 5 级：取指 IF → 译码/取数 ID → 执行 EX → 访存 MEM → 写回 WB），允许多条指令在时间上重叠执行，提高吞吐量。

**流水线加速比**：理论上 = 流水线级数（假设各阶段平衡）

**流水线冒险（Hazard）**：阻止下一条指令在指定时钟周期执行的情况。

1. **结构冒险（Structural Hazard）**：硬件资源冲突
   - 例：指令和数据共用一个存储器，IF 和 MEM 同时访问导致冲突
   - 解决：增加硬件资源（分离 I-cache/D-cache，多端口存储器）、指令停顿

2. **数据冒险（Data Hazard）**：指令间存在数据依赖
   - **RAW（Read After Write）**：先写后读的真依赖（如 `add $1, $2, $3; sub $4, $1, $5`）
   - **WAR（Write After Read）**：先读后写的反依赖（寄存器重命名消除）
   - **WAW（Write After Write）**：写写的输出依赖（寄存器重命名消除）
   - 解决：
     - **流水线停顿（插入气泡）**：简单但损失性能
     - **数据旁路（Forwarding / Bypassing）**：将 EX/MEM 和 MEM/WB 阶段的结果直接转发给下一条指令的 EX 阶段
     - **编译器调度**：重排指令填充延迟槽

3. **控制冒险（Control Hazard）**：分支指令导致下一条指令不确定
   - 例：beq, j, jal 等改变 PC 的指令
   - 解决：
     - **停顿**：等待分支条件确定后再取指（损失大）
     - **预测（Branch Prediction）**：静态预测（总预测不跳转 / 预测跳转）、动态预测（1-bit, 2-bit 饱和计数器，局部/全局/混合预测器，tournament predictor）
     - **分支延迟槽（Branch Delay Slot）**：编译器将分支指令前的有用指令填入延迟槽
     - **乱序执行**： Tomasulo 算法 + 重排序缓冲 ROB

**问题 11：什么是虚拟存储器？说明页式存储和段式存储的区别**

**答题要点**：

**虚拟存储器**：为每个程序提供一个比物理内存大得多的虚拟地址空间，操作系统负责虚拟地址到物理地址的映射。

**目的**：
- 扩大可用内存空间（借助磁盘）
- 简化编程模型（每个程序看到统一的线性地址空间）
- 内存保护（用户程序不能访问 OS 内存和其他程序内存）
- 进程隔离

**页式存储（Paging）**：
- 将虚拟地址空间划分为**固定大小**的页（如 4KB）
- 物理内存划分为同样大小的页帧（page frame）
- 地址映射：**页表（Page Table）** 记录虚拟页号 → 物理页帧号
- 虚拟地址 = 虚拟页号 (VPN) + 页内偏移
- 物理地址 = 物理页帧号 (PPN) + 页内偏移
- TLB（Translation Lookaside Buffer）：缓存常用的 VPN→PPN 映射，加速地址翻译

**段式存储（Segmentation）**：
- 将地址空间划分为**不同大小**的段（如代码段、数据段、堆段、栈段）
- 虚拟地址 = 段号 + 段内偏移
- 段表记录段基地址 + 段限长 + 权限位
- 优点：符合程序逻辑结构，便于分段共享和保护
- 缺点：段长不同，换入换出产生外部碎片（类似内存分配的 first-fit/best-fit 问题）

**段页式**：先分段，段内再分页，结合两者优点（Linux/Windows 本质是页式，但也用段寄存器保护）

**页面置换算法（页错误处理）**：
- FIFO（Belady 异常：增加页帧数可能增加页错误）
- LRU（理论最优近似，硬件实现困难，常用近似 LRU：时钟算法/增强时钟算法）
- OPT（理想算法，替换最远将来使用的页，仅作理论基准）
- Working Set（工作集模型，保证常驻工作集在内存中避免颠簸）

**问题 12：描述 CPU 的基本组成和各部件功能**

**答题要点**：

**经典冯·诺依曼结构 CPU**：

1. **运算器（ALU, Arithmetic Logic Unit）**：
   - 执行算术运算（加、减、乘、除、移位）和逻辑运算（与、或、非、异或、比较）
   - 配套：通用寄存器组（存放操作数和中间结果）、状态标志寄存器（零标志 ZF、符号标志 SF、溢出标志 OF、进位标志 CF）

2. **控制器（Control Unit, CU）**：
   - 产生控制信号，指挥整个系统按指令执行
   - 组成：程序计数器 PC（存下条指令地址）、指令寄存器 IR（存当前指令）、控制信号产生电路
   - 两种实现：
     - **硬布线控制器**：用组合逻辑电路直接产生控制信号（速度快，修改难，适合 RISC）
     - **微程序控制器**：将每条指令分解为微指令序列存放在控制存储器 CM 中（灵活，适合 CISC，速度稍慢）

3. **存储器（与 CPU 交互）**：
   - 寄存器 → L1 Cache（I/D 分离）→ L2 Cache → L3 Cache → 主存 → 磁盘
   - 通过总线与 CPU 连接

4. **输入/输出接口**：
   - I/O 设备与 CPU/主存之间的数据通路
   - I/O 方式：程序查询方式、中断方式、DMA 方式、通道方式

**现代 CPU（超标量 + 乱序执行 + 推测执行）**：
- 取指单元（IFU）+ 分支预测器
- 指令队列 / 指令窗口
- 指令解码 / 微码翻译（CISC）
- 寄存器重命名（消除 WAR/WAW 依赖）
- 保留站 / 发射队列（乱序调度）
- 多个执行单元（ALU, FP, Load/Store, Branch 并行）
- 重排序缓冲 ROB（保证顺序提交）
- Load/Store 队列（处理内存依赖）

**问题 13：什么是中断？描述中断的处理过程**

**答题要点**：

**中断（Interrupt）**：CPU 暂停当前程序的执行，转去处理更紧急的事件（I/O 完成、定时器、异常），处理完毕后返回被中断程序继续执行。

**中断分类**：
- **可屏蔽中断 INTR**：来自外部 I/O 设备，可用中断允许标志 IF 屏蔽
- **不可屏蔽中断 NMI**：如电源掉电、内存奇偶校验错，必须响应
- **内部中断/异常（Exception）**：指令执行出错（如除零、缺页、非法指令）
- **软中断 / 系统调用**：程序主动触发（如 x86 的 `int 0x80`, `syscall`）

**中断处理过程**：

1. **中断请求（IRQ）**：中断源通过中断控制器向 CPU 发请求信号
2. **中断响应**：
   - CPU 在每条指令末尾检查中断请求
   - 若允许（IF=1）且无更高优先级中断，开始响应
   - **保护断点**：将当前 PC（或 CS:IP）和程序状态字（PSW/EFLAGS）压入栈
   - **关中断**：清除 IF（保护中断服务程序不被打断，除非显式开中断）
   - **识别中断源**：从中断控制器读中断向量号
   - **转入中断服务程序**：根据中断向量表跳转
3. **中断服务（ISR 执行）**：
   - 保护现场（保存将要使用的寄存器到栈）
   - 执行中断处理逻辑
   - 恢复现场（从栈恢复寄存器）
4. **中断返回**：执行 `iret` 指令，从栈中恢复 PSW 和 PC，继续被中断的程序

**中断优先级**：
- 多个中断同时到达时，高优先级先处理
- 中断嵌套：高优先级中断可以打断低优先级中断服务程序
- 8259A 可编程中断控制器（PIC）负责中断优先级和屏蔽管理（现代系统用 APIC）

**与子程序调用的区别**：
- 子程序调用是程序员安排的（`call` 指令），中断是随机/异步的
- 子程序调用只需要保存返回地址，中断需要保存 PSW 和返回地址（以及相关寄存器）

**问题 14：描述浮点数的表示方法（IEEE 754）**

**答题要点**：

**IEEE 754 标准**是当前计算机浮点数的事实标准。

**表示公式**（规格化数）：
```
(-1)^S × (1.M) × 2^(E - bias)
```

其中：
- **S（符号位）**：0 = 正, 1 = 负
- **M（尾数/小数位 Mantissa）**：二进制小数，隐含整数部分 1
- **E（阶码 Exponent）**：偏移表示（无符号数 - bias = 真实阶码）
- **bias（偏移量）**：单精度 127，双精度 1023

**单精度（32位 float）**：
```
S(1) | E(8) | M(23)    = 32 位
```

**双精度（64位 double）**：
```
S(1) | E(11) | M(52)   = 64 位
```

**特殊值编码**：

| 情况 | E 值 | M 值 | 含义 |
|-----|------|------|------|
| 规格化数 | 0 < E < 255 | 任意 | ±1.M × 2^(E-127) |
| 非规格化数 | E = 0 | M ≠ 0 | ±0.M × 2^(-126)（gradual underflow）|
| 零 | E = 0 | M = 0 | ±0（有正负零之分）|
| 无穷大 | E = 255 | M = 0 | ±∞（溢出结果）|
| NaN | E = 255 | M ≠ 0 | Not a Number（0/0, ∞-∞ 等无意义运算）|

**例子**：
- `1.0` (float): S=0, E=127 (二进制 01111111), M=0 → `0x3F800000`
- `0.5` (float): S=0, E=126, M=0 → `0x3F000000`
- `-1.5` (float): S=1, E=127, M=1.1 即二进制 100...0 → `0xBFC00000`

**浮点数特点**：
- 范围大（单精度约 ±10³⁸，双精度约 ±10³⁰⁸）
- **精度有限**（23 位尾数 ≈ 7 位十进制有效数字）
- **不满足结合律**：(a+b)+c ≠ a+(b+c)（舍入误差累积不同）
- 比较：NaN ≠ 任何数（包括自己），-0 = +0

### 三、操作系统（15-22）

**问题 15：什么是进程？什么是线程？它们的区别和关系**

**答题要点**：

**进程（Process）**：程序的一次执行过程，是操作系统进行资源分配和调度的基本单位。
- 资源拥有者：拥有独立的地址空间（代码段、数据段、堆、栈、文件、打开的设备）
- 包含：进程控制块 PCB、程序代码、数据、程序计数器、寄存器、打开文件表、信号处理配置

**线程（Thread）**：进程内的执行流，是 CPU 调度的基本单位。
- 共享所属进程的资源（地址空间、文件、信号）
- 拥有：线程 ID、程序计数器、寄存器集合、栈（独立的函数调用栈）、线程局部存储 (TLS)

**区别**：

| 特性 | 进程 | 线程 |
|-----|------|------|
| 资源拥有 | 独立资源，是分配单位 | 共享进程资源，基本不拥有资源 |
| 调度单位 | 传统 OS 的调度单位 | 现代 OS 的 CPU 调度单位 |
| 上下文切换 | 慢（切换页表、TLB 失效） | 快（只切换寄存器和栈） |
| 通信方式 | IPC（管道、消息队列、共享内存、信号量、套接字）| 直接读写进程内存（需同步） |
| 健壮性 | 一个进程崩溃不影响其他进程 | 一个线程崩溃可能导致整个进程崩溃 |
| 创建/销毁开销 | 大（需分配/回收资源）| 小（只分配/回收线程栈）|

**多对多关系**：
- 单线程进程（传统 UNIX）：一个进程 = 一个线程
- 多线程进程（现代系统）：一个进程有多个线程
- 内核线程 vs 用户线程：用户态线程库管理（如 Linux 的 NPTL 是 1:1 模型，每个用户线程对应一个内核线程）

**为什么用多线程**：
- 多核并行：充分利用多个 CPU 核心
- I/O 重叠：一个线程等待 I/O 时，其他线程继续计算
- 响应性：GUI 程序中，耗时任务放后台线程，主线程保持响应

**问题 16：进程调度算法有哪些？比较它们的特点**

**答题要点**：

**批处理系统调度**：

1. **FCFS（First-Come First-Served，先来先服务）**：
   - 非抢占，按到达顺序执行
   - 优点：公平、简单
   - 缺点：平均等待时间长（短作业排在长作业后体验差）、护航效应（Convoy Effect）

2. **SJF（Shortest Job First，最短作业优先）**：
   - 选择执行时间最短的作业
   - 理论最优（平均等待时间最小）
   - 缺点：需要预知作业时间；可能饥饿（长作业永远排不到）
   - **抢占版 SRTF（Shortest Remaining Time First）**：新作业剩余时间比当前短则抢占

3. **优先级调度**：
   - 每个进程有优先级，选最高优先级
   - 优先级可以静态（系统规定）或动态（根据资源使用情况调整）
   - **多级反馈队列（Multi-level Feedback Queue）**：最通用，综合考虑 I/O 密集型和 CPU 密集型
     - 多个队列，优先级递减，时间片递增
     - 新进程进入最高优先级队列
     - 用完时间片降到下一级（惩罚 CPU 密集型）
     - I/O 后返回原级（奖励 I/O 密集型）
     - 长时间等待的进程可以升级（防止饥饿）

**实时系统调度**：

4. **RM（Rate-Monotonic，速率单调）**：
   - 静态优先级，周期越短优先级越高
   - 理论最优静态算法，CPU 利用率 ≤ n(2^(1/n)-1)，n→∞ 时约 69%

5. **EDF（Earliest Deadline First，最早截止时间优先）**：
   - 动态优先级，截止时间越早优先级越高
   - 理论最优动态算法，可达到 100% CPU 利用率（在可调度前提下）

**Linux CFS（Completely Fair Scheduler）**：
- 红黑树管理可运行进程，按虚拟运行时间（vruntime）排序
- 每次选 vruntime 最小的进程运行
- 追求"完全公平"，给每个进程公平的 CPU 时间
- 按权重分配时间片（nice 值影响权重）

**衡量指标**：
- CPU 利用率、吞吐量、周转时间、等待时间、响应时间
- 公平性、实时性、防止饥饿

**问题 17：什么是死锁？死锁的四个必要条件和处理方法**

**答题要点**：

**死锁（Deadlock）**：多个进程互相等待对方占用的资源，导致所有进程都无法继续执行的状态。

**死锁的四个必要条件（Coffman Conditions）**：

1. **互斥（Mutual Exclusion）**：资源不能被共享，一次只能被一个进程使用
2. **占有并等待（Hold and Wait）**：进程至少持有一个资源，同时请求其他进程持有的资源
3. **不剥夺（No Preemption）**：资源只能由持有者主动释放，不能被强行抢占
4. **循环等待（Circular Wait）**：存在一个进程-资源的循环链 P₁→P₂→...→Pₙ→P₁

**以上四个条件必须同时满足才可能产生死锁。**

**处理死锁的四种策略**：

1. **忽略死锁（鸵鸟算法）**：
   - 假设死锁永远不发生，发生后重启系统
   - 用于死锁极少发生且代价可接受的系统（如大多数桌面 OS）

2. **预防死锁（Deadlock Prevention）**：破坏四个必要条件之一
   - 破坏互斥：使资源可共享（如只读文件，现代技术如 RCU 锁）
   - 破坏占有并等待：一次性申请所有所需资源；或者申请新资源前释放所有资源
   - 破坏不剥夺：允许 OS 强行从进程抢占资源（如银行家算法中的请求<持有则释放）
   - 破坏循环等待：对资源按序号排序，进程只能按序号递增请求资源

3. **避免死锁（Deadlock Avoidance）**：动态检查资源分配状态，确保系统始终处于安全状态
   - **安全状态**：存在某种进程执行顺序（安全序列），使所有进程都能完成
   - **银行家算法（Banker's Algorithm）**：Dijkstra 提出
     - 数据结构：Available（剩余资源）, Max（进程最大需求）, Allocation（已分配）, Need（剩余需求）
     - 每次请求：先假设分配，然后检查系统是否仍安全；是则真分配，否则等待
   - 缺点：需要预知进程最大需求，进程数和资源数固定，实际很少直接用

4. **检测并恢复（Deadlock Detection and Recovery）**：
   - 允许死锁发生，但定期检测
   - **资源分配图（RAG）**：若资源分配图中存在环且环中每种资源只有一个实例，则存在死锁
   - 检测方法：拓扑排序检测环（类似银行家算法的 Need ≤ Available 模拟）
   - 恢复：
     - **进程终止**：终止所有死锁进程（代价高）；逐个终止直到死锁解除
     - **资源剥夺**：从死锁进程中抢占资源分配给其他进程（需谨慎选择被剥夺者，避免活锁）
     - **回滚**：将进程回滚到安全检查点重新执行

**问题 18：描述页面置换算法（FIFO、LRU、OPT、时钟算法）**

**答题要点**：（参见问题 11 的页面置换部分补充，这里给出更详细的比较）

当产生缺页（所访问的页不在内存）且内存已满时，需要选择一页换出到磁盘。

**OPT / Belady 最优算法**：替换**最远将来才会使用**的页
- 理论最优，命中率上界
- 缺点：需要预知未来访问序列，实际不可行
- 用途：作为理论基准评估其他算法

**FIFO（先进先出）**：替换最早进入内存的页
- 实现：维护一个队列，新页加入队尾，替换队头
- 优点：简单
- 缺点：**Belady 异常**：增加物理页帧数，缺页次数反而可能增加
- 可能替换频繁使用的"热"页面

**LRU（Least Recently Used，最近最少使用）**：替换**最久未使用**的页
- 基于局部性原理：最近没用到的，将来也可能不用
- 理想实现：用栈/链表，每次访问将页移到栈顶，替换栈底
- 近似实现：
  - **时钟算法（Clock Algorithm / Not Recently Used）**：环形链表 + 使用位 use_bit
    - 指针循环查找：遇到 use_bit=0 则替换；遇到 use_bit=1 则置 0 继续
  - **增强时钟算法**：增加修改位 dirty，优先替换未修改的页（不需要写回磁盘）
  - **最不常用 LFU**：替换访问次数最少的页（需要计数器，可能长期不用的页仍保留）
- 接近 OPT 性能，无 Belady 异常
- 缺点：严格 LRU 硬件支持复杂（需要时间戳或栈），实际 OS 多使用近似算法

**工作集模型（Working Set）**：
- 工作集 W(t, Δ) = 进程在时间窗口 [t-Δ, t] 内访问的页集合
- 核心思想：保证进程的工作集始终在内存中，否则会发生"抖动"（Thrashing）
- 抖动：频繁的页面换入换出，CPU 大部分时间用于处理缺页

**问题 19：什么是文件系统？描述常见文件系统（ext, NTFS, FAT32）的特点**

**答题要点**：

**文件系统**：操作系统中负责管理和存储文件信息的软件。提供文件的组织、存储、检索、命名、共享和保护。

**核心概念**：
- 文件：字节序列（UNIX 哲学：一切皆文件）
- 目录：特殊文件，存储文件名到 inode/文件控制块的映射
- inode（UNIX/Linux）：存储文件元数据（大小、权限、所有者、时间戳、数据块指针），不包含文件名
- 硬链接：多个文件名指向同一 inode（同一文件）
- 软链接/符号链接：一个文件存储另一个文件的路径

**常见文件系统**：

1. **ext2/ext3/ext4（Linux 主流）**：
   - **ext2**：经典 UNIX 文件系统，无日志
   - **ext3**：ext2 + 日志（三种模式：journal, ordered, writeback），崩溃恢复快
   - **ext4**：ext3 增强版（extents 代替间接块、延迟分配、最大支持 1EB 分区、16TB 文件、目录项索引、预分配）
   - 特点：稳定、成熟、适合服务器

2. **FAT16/FAT32（File Allocation Table）**：
   - 微软早期文件系统，用于 DOS/Win9x
   - 结构：文件分配表（FAT）是一个数组，每个表项记录下一个簇号
   - 缺点：不支持大文件（FAT32 单文件最大 4GB）、无权限、效率低（大分区 FAT 表大）、无日志
   - 优点：简单、兼容性好（几乎所有 OS 都支持），常用在 U 盘/SD 卡

3. **NTFS（New Technology File System，Windows 主流）**：
   - 特性：日志（恢复）、权限（ACL）、压缩、加密（EFS）、配额、稀疏文件、重解析点（支持符号链接、挂载点）
   - MFT（主文件表）：每个文件/目录在 MFT 中有一个记录（类似 inode，但更复杂）
   - 支持大文件（理论最大 16EB）

4. **其他**：
   - **XFS**（SGI 开发，高性能日志文件系统，适合大文件和大存储，RHEL/CentOS 7+ 默认）
   - **Btrfs（B-tree FS）**：Copy-on-write 文件系统，支持快照、子卷、RAID、校验和、在线调整（Oracle/SUSE 推动）
   - **ZFS**：Sun/Oracle，先进的 128 位文件系统 + 卷管理器组合，端到端数据校验、快照、压缩、RAID-Z
   - **APFS**：Apple File System，macOS/iOS 新文件系统，COW、快照、加密

**文件系统性能优化**：
- 缓存：Page Cache / Buffer Cache（内存缓存磁盘数据）
- 预读（Read-ahead）：预测性预读
- 延迟分配（Delayed allocation）：积累写操作再分配磁盘块（减少碎片）
- 碎片整理：分散的文件块重新连续排列
- 目录索引（如 HTree/DirIndex）：大目录查找优化

**问题 20：什么是系统调用？描述 read/write/fork/exec 的工作原理**

**答题要点**：

**系统调用（System Call）**：用户程序请求操作系统内核提供服务的接口。
- 为什么需要：用户态程序不能直接执行特权操作（访问硬件、修改页表、I/O），必须通过内核
- 触发方式：特殊 CPU 指令（x86: `int 0x80` / `sysenter` / `syscall`；ARM: `svc`）
- 过程：用户态 → 陷入内核态（trap）→ 查系统调用表 → 执行内核函数 → 返回用户态

**read()**：从文件描述符读取数据
```c
ssize_t read(int fd, void *buf, size_t count);
```
- 内核流程：检查 fd 和 buf 有效性 → 查文件表 → 通过文件系统读取数据（可能从 Page Cache 命中，或触发磁盘 I/O）→ 从内核缓冲区复制到用户缓冲区（注意地址空间隔离）→ 返回读取字节数

**write()**：向文件描述符写入数据
```c
ssize_t write(int fd, const void *buf, size_t count);
```
- 内核流程：检查参数 → 从用户缓冲区复制到内核缓冲区 → 通常先写入 Page Cache（由内核决定何时刷盘，fsync() 可强制）→ 返回写入字节数
- 延迟写：write 成功返回不代表数据已到磁盘（可能在 Page Cache）

**fork()**：创建子进程（UNIX 传统）
- 内核流程：
  1. 分配新的 pid 和 task_struct
  2. 复制父进程的资源：复制文件描述符表（共享文件指针）、复制信号处理配置
  3. **写时复制（Copy-on-Write, COW）**：父子进程共享页表，页标记为只读；任一方写入时触发缺页，内核复制新的物理页
  4. 子进程返回 0，父进程返回子进程 pid
- 注意：COW 使 fork 从"复制整个地址空间"变为"只复制页表"，大幅提升效率

**exec() 系列**（execve 是系统调用，其他是库函数包装）：用新程序替换当前进程
```c
int execve(const char *path, char *const argv[], char *const envp[]);
```
- 内核流程：
  1. 验证可执行文件（权限、格式，如 ELF）
  2. **释放旧的地址空间**（代码、数据、堆、栈）
  3. 根据 ELF 文件加载新程序的代码段、数据段
  4. 建立新的栈、堆（初始化 bss 段为 0）
  5. 设置 PC 指向程序入口（_start，最终调用 main）
  6. 不返回（成功时），失败时返回 -1
- fork + exec = 创建执行新程序的子进程（经典 UNIX 模式）

**问题 21：描述进程间通信（IPC）的方式**

**答题要点**：

Linux/Unix 常见 IPC 方式：

1. **管道（Pipe）**：
   - 半双工（单向数据流），用于有亲缘关系的进程（父子/兄弟）
   - `int pipe(int pipefd[2])`：pipefd[0] 读，pipefd[1] 写
   - 内核缓冲区（通常 4KB），按 FIFO 传递字节流
   - **命名管道（FIFO / Named Pipe）**：mkfifo 创建，存在于文件系统中，无亲缘进程也可用

2. **消息队列（Message Queue）**：
   - 消息是结构化数据（不只是字节流），有类型/优先级
   - POSIX mq_* / System V msg_*
   - 优点：按消息类型读取，不用关心写入顺序；消息大小可独立配置
   - 缺点：需要显式创建/销毁，有最大消息数和大小限制

3. **共享内存（Shared Memory）**：
   - 将同一段物理内存映射到多个进程的虚拟地址空间
   - POSIX shm_open + mmap / System V shmget
   - **最快的 IPC**：不经过内核中转，进程直接读写内存
   - 缺点：需要配合同步机制（信号量/互斥锁）防止竞态条件

4. **信号量（Semaphore）**：
   - 本质是计数器 + 等待队列，用于同步互斥
   - P 操作（wait）：信号量 -1，若 < 0 则阻塞
   - V 操作（signal）：信号量 +1，若 ≤ 0 则唤醒一个等待进程
   - POSIX sem_t / System V sem_*
   - **互斥锁（Mutex）** = 二值信号量（0/1）

5. **信号（Signal）**：
   - 异步通知机制，发送短消息给进程
   - 常见信号：SIGKILL（终止，不可忽略不可捕获）、SIGTERM（优雅终止）、SIGINT（Ctrl+C）、SIGSEGV（段错误）、SIGCHLD（子进程终止通知父）
   - 处理方式：默认、忽略、自定义信号处理函数（signal handler）

6. **套接字（Socket）**：
   - 最通用的 IPC，支持跨机器网络通信
   - Unix Domain Socket（AF_UNIX）：本机高性能 IPC，比 TCP 快（不经过网络协议栈）
   - INET Socket（AF_INET/AF_INET6）：跨网络通信

7. **其他**：
- **内存映射文件（mmap）**：将文件映射到内存，可用于进程共享
- **门（Doors/Solaris）**、** futex（Linux 快速用户态互斥）**

**选择建议**：
- 简单字节流 + 亲缘进程：管道
- 不同机器：套接字
- 大数据 + 高性能：共享内存 + 信号量/互斥锁
- 结构化消息：消息队列
- 事件通知：信号 / eventfd

**问题 22：描述虚拟内存管理的实现（页表、TLB、缺页处理）**

**答题要点**：

**页表（Page Table）**：虚拟页号 (VPN) → 物理页帧号 (PPN) 的映射
- 每个进程有独立页表（PCB 中指向页表基地址）
- 页表项 PTE：包含 PPN + 标志位（有效位 V、读/写/执行权限 R/W/X、用户/内核位 U/S、修改位 D、访问位 A、全局位 G 等）

**多级页表（解决页表太大问题）**：
- 虚拟地址 = PML4 | PDPT | PDT | PT | Offset （x86-64 四级页表示意）
- 多级索引，只分配当前使用的叶子页表
- 节省空间：稀疏地址空间（如栈和堆之间的巨大空洞）不需要分配页表

**TLB（Translation Lookaside Buffer，转译后备缓冲器）**：
- CPU 内部的高速缓存，缓存近期使用的 VPN → PPN 映射
- 命中：直接得到 PPN，无需查内存中的多级页表（1 周期）
- 失效：需要"页表遍历（page walk）"查内存中的多级页表（数百周期）
- TLB miss 率对性能影响极大，是 OS 优化的重要目标

**缺页（Page Fault）处理流程**：

当 CPU 遇到虚拟地址的页表项 PTE.V = 0（无效），触发缺页异常（#PF），陷入内核：

1. **判断异常原因**（查 PTE 和地址）：
   - 地址非法（越界 / 访问未映射地址）→ 发送 SIGSEGV 终止进程
   - 权限违规（写只读页 / 用户态访问内核页）→ 发送 SIGSEGV
   - 合法地址但页不在内存 → 执行缺页处理

2. **合法缺页的处理**：
   - **写时复制（COW）**：fork 后的共享页被写入 → 分配新物理页并复制内容
   - **请求调页**：首次访问文件映射页 → 从文件系统读入
   - **交换页（swap）**：页被换出到磁盘 → 从 swap 分区读回
   - **匿名页**：首次访问 bss/栈/堆的新页 → 分配物理页并清零

3. **处理步骤（请求调页示例）**：
   - 在内核中查找可用物理帧（若无则触发页面置换换出一页）
   - 从文件/swap 读取数据到物理帧（I/O 期间进程阻塞，CPU 调度其他进程）
   - I/O 完成后更新页表：PTE.V=1，PPN=新分配的物理帧
   - 返回用户态，重新执行触发缺页的指令（这次会成功）

**性能影响**：
- 缺页处理需要磁盘 I/O（≈ 20ms vs 内存访问 ≈ 100ns，差 200,000 倍）
- 太多缺页 → 系统抖动（thrashing）→ 解决：增大内存 / 用工作集模型保证热点页常驻

### 四、计算机网络（23-28）

**问题 23：描述 OSI 七层模型和 TCP/IP 四层模型的对应关系**

**答题要点**：

**OSI 七层（理论模型）**：

1. **物理层（Physical）**：
   - 传输比特流 0/1，规定电压、接口、线缆规格
   - 设备：中继器、集线器 (Hub)
   - 协议/标准：RS-232, 光纤, 双绞线 (UTP Cat5e/6), Wi-Fi (PHY)

2. **数据链路层（Data Link）**：
   - 将比特组织为帧 (frame)，在相邻节点间传输
   - 功能：成帧、物理寻址 (MAC)、差错检测 (CRC)、流量控制
   - 设备：交换机 (Switch, 二层)、网卡 (NIC)
   - 协议：Ethernet, PPP, HDLC, ARP（介于 2/3 层之间）

3. **网络层（Network）**：
   - 端到端路径选择，将分组 (packet/datagram) 从源送到目的
   - 功能：逻辑寻址 (IP)、路由选择、拥塞控制、网际互联
   - 设备：路由器 (Router, 三层)
   - 协议：IP, ICMP, OSPF, BGP

4. **传输层（Transport）**：
   - 进程到进程的数据传输
   - 功能：端口号标识进程、可靠传输 (TCP)、流量控制、拥塞控制
   - 协议：TCP（面向连接，可靠）, UDP（无连接，不可靠，高效）

5. **会话层（Session）**：
   - 建立、管理、终止会话（进程间对话），提供检查点/恢复机制
   - 实际网络中很少独立存在，通常合并到应用层

6. **表示层（Presentation）**：
   - 数据格式转换、加密解密、压缩解压缩
   - 例：ASN.1, TLS/SSL（常被当作会话/表示层的实现）

7. **应用层（Application）**：
   - 为用户应用程序提供网络服务
   - 协议：HTTP, HTTPS, FTP, SMTP, DNS, SSH, Telnet

**TCP/IP 四层（实际使用模型）**：

1. **网络接口层（Link Layer）** = OSI 物理层 + 数据链路层
2. **网络层（Internet Layer）** = OSI 网络层
3. **传输层（Transport Layer）** = OSI 传输层
4. **应用层（Application Layer）** = OSI 会话层 + 表示层 + 应用层

**数据封装（Encapsulation）**：
- 应用层数据 → 加 TCP/UDP 头 → 段（segment）
- 加 IP 头 → 分组/数据报（packet/datagram）
- 加 Ethernet 头 → 帧（frame）
- 编码为比特流 → 物理传输

**问题 24：TCP 三次握手和四次挥手的过程？为什么这样设计？**

**答题要点**：

**三次握手（建立连接）**：

```
Client                          Server
  | SYN (seq=x)                   |
  | ----------------------------->|
  |                               |
  |    SYN+ACK (seq=y, ack=x+1)   |
  | <-----------------------------|
  |                               |
  | ACK (seq=x+1, ack=y+1)        |
  | ----------------------------->|
  |                               |
  |      (ESTABLISHED 连接建立)   |
```

- **SYN（同步）**：发起方选择初始序列号（ISN, Initial Sequence Number）
- **ACK（确认）**：确认收到对方的 SYN，ack 号 = 对方 seq + 1
- 第 3 次握手的 ACK 可以携带数据（Piggybacking）

**为什么三次握手（不是两次或四次）**：

1. **确认双方收发能力**：Client 发 SYN → Server 知道 Client 能发、Server 能收；Server 回 SYN+ACK → Client 知道双方收发都正常；Client 发 ACK → Server 知道 Client 能收
2. **防止过期连接请求**（经典原因）：若只有两次握手，历史上滞留在网络中的旧 SYN 可能在 Server 端创建无效连接（如 Client 早已关闭）。三次握手中 Client 可通过 ACK 拒绝或忽略旧连接。
3. **同步序列号**：双方需要交换 ISN，四次也行但第 2、3 步可合并（SYN+ACK），因此三次最优

**四次挥手（关闭连接）**：

```
Client                          Server
  | FIN (seq=u)                   |
  | ----------------------------->| (CLOSE_WAIT)
  |                               |
  | ACK (seq=u+1)                 |
  | <-----------------------------| (Client: FIN_WAIT_2)
  |                               |
  |      FIN (seq=v)              |
  | <-----------------------------| (Server 应用层也写完了)
  |                               |
  | ACK (seq=v+1)                 |
  | ----------------------------->| (Server: CLOSED)
  | (TIME_WAIT 等待 2*MSL)        |
  |         CLOSED                |
```

- **全双工关闭**：TCP 是全双工，两个方向独立关闭，各需一个 FIN 和一个 ACK
- **TIME_WAIT 状态**：主动关闭方等待 2×MSL（最大分段生存时间，通常 2 分钟）
  - 理由 1：保证最后一个 ACK 能被对方收到（若丢失，对方会重传 FIN，我们还能再次 ACK）
  - 理由 2：防止新连接收到旧连接的延迟报文（2×MSL 保证旧报文消失）

**问题 25：TCP 如何保证可靠传输？（序号、确认、重传、流量控制、拥塞控制）**

**答题要点**：

TCP 的可靠传输由多个机制协同工作：

1. **序号和确认号（Sequence & Acknowledgment Numbers）**：
   - TCP 对每个字节编号（序号是字节流的编号，不是报文编号）
   - ACK = 期望收到的下一个字节序号（累计确认：ACK n 表示 n 之前的字节都已收到）
   - 接收方可以延迟 ACK（最多 500ms，通常在收到第二个报文段时捎带确认）

2. **超时重传（Retransmission）**：
   - 发送方维护 RTO（Retransmission TimeOut）超时计时器
   - RTT（Round-Trip Time）测量：采样 RTT → 用平滑算法计算 SRTN（Smoothed RTT）和 RTTVAR（RTT 方差）→ RTO = SRTN + 4×RTTVAR
   - 超时后重传最早的未 ACK 报文段，并加倍 RTO（指数退避）

3. **快速重传（Fast Retransmit）**：
   - 接收方收到乱序报文立即发送重复 ACK（不延迟）
   - 发送方收到 **3 个重复 ACK**（共 4 个相同 ACK）立即重传，不必等待 RTO 超时
   - 比超时重传快得多（毫秒级 vs RTO 通常数百毫秒）

4. **流量控制（Flow Control）**：
   - 接收方在 TCP 头部通告接收窗口大小（rwnd, Receiver Window）
   - 发送方实际发送窗口 = min(cwnd, rwnd)，避免发送太快使接收方缓冲区溢出
   - 接收方 rwnd = 0 时，发送方停止发送，改为发送探测报文（window probe）

5. **拥塞控制（Congestion Control）**：
   - 经典算法（Tahoe, Reno, NewReno）：
     - **慢启动（Slow Start）**：cwnd 每个 RTT 翻倍（实际每个 ACK +1 MSS，指数增长）直到达到 ssthresh
     - **拥塞避免（Congestion Avoidance）**：cwnd ≥ ssthresh 时，每个 RTT +1 MSS（线性增长）
     - **超时重传**：ssthresh = cwnd/2, cwnd = 1 MSS（激进降窗）
     - **3 个重复 ACK**：ssthresh = cwnd/2, cwnd = ssthresh（快重传 + 快恢复 Fast Recovery）
   - 现代算法：CUBIC（Linux 默认，比 Reno 更"平滑"，适合高速网络）、BBR（Google, 基于模型，主动探测带宽和 RTT）

**问题 26：比较 TCP 和 UDP 的区别和适用场景**

**答题要点**：

| 特性 | TCP（Transmission Control Protocol） | UDP（User Datagram Protocol） |
|-----|-----|-----|
| 连接性 | 面向连接（三次握手建立连接） | 无连接（无需握手） |
| 可靠性 | 可靠：确认、重传、序号保证顺序 | 不可靠：不保证送达，不保证顺序 |
| 流量/拥塞控制 | ✓（滑动窗口、拥塞控制） | ✗（应用层自己处理） |
| 首部开销 | 20 字节（最小）+ 选项 | 8 字节（固定） |
| 传输方式 | 字节流（无边界概念） | 数据报（保留消息边界） |
| 实时性 | 低（重传和拥塞控制带来延迟） | 高（发即走，无额外延迟） |
| 吞吐量 | 受拥塞控制限制，可能保守 | 应用可控，可全速发送 |
| 连接数 | 每对 (src_ip:port, dst_ip:port) 一个连接 | 无连接概念，一个 socket 可发往多方 |

**TCP 适用场景**：
- 需要可靠传输：HTTP/HTTPS, FTP, SMTP, SSH
- 文件传输（FTP, SCP）
- 邮件传输（SMTP, IMAP, POP3）
- Web 浏览（HTTP/1.x, HTTP/2）
- 数据库连接（MySQL, PostgreSQL）
- 远程登录（SSH, Telnet）
- 注意：HTTP/3 使用 QUIC（基于 UDP）实现可靠传输

**UDP 适用场景**：
- 实时应用：视频会议、直播、VOIP（丢一点包比延迟增大更可接受）
- 游戏：多人在线游戏（对延迟敏感，丢包可通过应用层补偿）
- DNS：简短请求-响应，UDP 更快，失败可重试
- 广播/多播：UDP 支持多播和广播，TCP 不支持
- QUIC（HTTP/3）：在 UDP 上实现 TCP 的可靠 + TLS 加密 + 多路复用
- 物联网：低带宽、低功耗设备

**问题 27：描述 HTTP 和 HTTPS 的区别，以及 HTTPS 的工作原理**

**答题要点**：

**HTTP vs HTTPS**：

| 特性 | HTTP | HTTPS |
|-----|------|-------|
| 全称 | HyperText Transfer Protocol | HTTP Secure |
| 默认端口 | 80 | 443 |
| 安全性 | 明文传输，可被窃听/篡改/伪造身份 | TLS/SSL 加密，可防窃听/篡改/身份伪造 |
| 性能 | 快，无加密开销 | 稍慢（握手 + 加解密），现代硬件 + TLS 1.3 已接近 HTTP |
| URL 前缀 | http:// | https:// |
| 证书 | 不需要 | 需要 CA 颁发的数字证书 |
| 浏览器标识 | 无锁标志 / "不安全"警告 | 绿色/灰色锁图标 |

**HTTPS = HTTP + TLS（Transport Layer Security），前身是 SSL**

**TLS 握手过程（TLS 1.2 简化版）**：

```
Client                          Server
  | ClientHello                  |  (随机数 + 支持的密码套件 + 会话ID)
  | ----------------------------->|
  |                               |
  | ServerHello                   |  (选择密码套件 + 服务器随机数)
  | Certificate (服务器证书)       |  (包含公钥，由 CA 签名验证身份)
  | ServerKeyExchange (可选)       |  (DHE/ECDHE 需要额外交换密钥参数)
  | ServerHelloDone               |
  | <-----------------------------|
  |                               |
  | ClientKeyExchange             |  (预主密钥 Pre-Master Secret，用服务器公钥加密)
  | [ChangeCipherSpec]            |  (通知：后续消息用新密钥加密)
  | Encrypted Handshake Message   |  (加密 Finished，包含握手摘要，验证握手无篡改)
  | ----------------------------->|
  |                               |
  | [ChangeCipherSpec]            |
  | Encrypted Handshake Message   |
  | <-----------------------------|
  |                               |
  |      加密 HTTP 数据传输        |
  | <============================>|
```

**密钥导出**：Client Random + Server Random + Pre-Master Secret → 主密钥 Master Secret → 导出四个会话密钥（Client→Server 加密密钥、Server→Client 加密密钥、两个方向的 MAC 密钥）

**TLS 1.3 改进**：
- 1-RTT 握手（甚至 0-RTT 恢复连接），延迟降低
- 删除所有弱密码套件，强制前向安全
- 简化协议，攻击面减少

**核心安全保障**：
1. **保密性**：对称加密（AES, ChaCha20）
2. **完整性**：MAC（HMAC-SHA256, Poly1305）或 AEAD
3. **身份认证**：非对称加密 + 数字证书（X.509）+ CA 信任链
4. **前向安全（Forward Secrecy）**：使用 DHE/ECDHE 密钥交换，长期密钥泄露不影响历史会话解密

**问题 28：描述 DNS 的工作原理和域名解析过程**

**答题要点**：

**DNS（Domain Name System）**：分布式数据库，将人类可读的域名（如 www.nju.edu.cn）翻译成 IP 地址。

**域名结构（分层）**：`主机名.二级域.顶级域`（从右到左层级降低）
- 根域 `.`（13 组根服务器，A-M）
- 顶级域 TLD：`.com`（通用）、`.cn`（国家）、`.edu`（教育机构）
- 二级域：`.com.cn`, `.edu.cn`
- 三级域（组织域名）：`nju.edu.cn`
- 子域 / 主机名：`www.nju.edu.cn`, `cs.nju.edu.cn`

**DNS 解析过程（以查询 www.nju.edu.cn 为例）**：

1. **浏览器/操作系统缓存检查**：是否已有该域名的缓存记录？是则直接返回。
2. **查询本地 DNS 解析器（Resolver）**：通常是 ISP 的 DNS 服务器或公共 DNS（8.8.8.8 Google, 114.114.114.114 国内）
3. **递归查询（Resolver → 根服务器）**：
   - 本地服务器向**根服务器**查询 `www.nju.edu.cn`
   - 根服务器不直接回答，返回 `.cn` TLD 服务器地址
4. **迭代查询（Resolver → TLD → 权威服务器）**：
   - 本地服务器向 `.cn` TLD 服务器查询 → 返回 `.edu.cn` 权威服务器地址
   - 向 `.edu.cn` 权威服务器查询 → 返回 `nju.edu.cn` 的权威 DNS 服务器
   - 向南大 DNS 服务器查询 → 返回 `www.nju.edu.cn` 的 IP 地址
5. **本地 DNS 服务器缓存结果**并返回给用户
6. **用户浏览器缓存结果**并发起 HTTP/HTTPS 连接

**递归 vs 迭代**：
- **递归查询**：客户端 → 本地 DNS，客户端说"给我最终答案，找不到就说找不到"
- **迭代查询**：本地 DNS → 根/TLD/权威，每次说"我不知道答案，但知道问谁"

**DNS 记录类型**：
- **A**：域名 → IPv4 地址
- **AAAA**：域名 → IPv6 地址
- **CNAME**：域名 → 另一个域名（别名，如 www.example.com → example.com）
- **MX**：邮件交换服务器
- **NS**：权威名称服务器
- **TXT**：任意文本（用于 SPF/DKIM 防邮件伪造、域名所有权验证）
- **PTR**：反向 DNS（IP → 域名）

**DNS 性能/安全问题**：
- **缓存机制**：DNS 记录有 TTL（存活时间），平衡一致性和性能
- **DNS 劫持**：恶意篡改 DNS 响应（运营商劫持、路由器 DNS 被改）
- **DNS 污染**：伪造响应注入错误解析结果（防翻墙手段）
- **DNS over HTTPS (DoH)** / **DNS over TLS (DoT)**：加密 DNS 查询，防窃听和篡改
- **CDN**：利用 DNS 的多 IP 响应实现就近访问（智能 DNS 根据地理位置返回不同 IP）

### 五、软件工程与综合（29-30）

**问题 29：描述你熟悉的一个软件开发模型（瀑布、敏捷、Scrum）**

**答题要点**：

**瀑布模型（Waterfall）**：
- 顺序流程：需求分析 → 设计 → 实现 → 测试 → 部署 → 维护
- 特点：阶段分明，文档驱动，下一阶段开始前必须完成上一阶段
- 优点：简单易管理，适合需求稳定、技术成熟的项目（如政府合同）
- 缺点：不灵活，难以适应需求变更；集成测试在后期，发现问题代价高
- 适用：需求明确、不易变更的小项目

**敏捷开发（Agile）**：
- **核心价值观**（敏捷宣言）：
  1. 个体和交互 高于 流程和工具
  2. 可工作的软件 高于 详尽的文档
  3. 客户合作 高于 合同谈判
  4. 响应变化 高于 遵循计划
- **12 个原则**：尽早交付、拥抱变化、频繁迭代、业务人员与开发者协作等

**Scrum（最流行的敏捷框架）**：

**三大角色**：
1. **Product Owner（产品负责人）**：定义需求、排优先级（Product Backlog）、代表客户利益
2. **Scrum Master**：主持 Scrum 过程、移除障碍、保护团队不被打扰（不是项目经理）
3. **Development Team（开发团队）**：3-9 人跨职能团队，自组织地完成工作

**三个工件**：
1. **Product Backlog（产品待办列表）**：所有需求/功能清单，有序
2. **Sprint Backlog（迭代待办列表）**：当前迭代要完成的任务
3. **Product Increment（产品增量）**：每个 Sprint 结束时的可交付产品

**五个事件**：
1. **Sprint（迭代）**：2-4 周，固定时长
2. **Sprint Planning（迭代计划会）**：8 小时内，确定本迭代目标和任务
3. **Daily Scrum（每日站会）**：15 分钟，每人回答"昨天做了什么/今天计划/有什么障碍"
4. **Sprint Review（评审会）**：4 小时内，向利益相关者演示可工作的软件，收集反馈
5. **Sprint Retrospective（回顾会）**：3 小时内，团队反思改进过程

**与传统的区别**：
- 增量式而非顺序式
- 拥抱变化而非冻结需求
- 人治（团队自组织）而非法治（详细流程文档）
- 可工作的软件是进度的主要度量

**问题 30：什么是设计模式？列举几个你熟悉的设计模式（单例、工厂、观察者、策略）**

**答题要点**：

**设计模式（Design Pattern）**：在软件设计中针对常见问题的通用、可复用的解决方案。
- GoF（Gang of Four）《设计模式》一书提出 23 种经典设计模式
- 分为三大类：**创建型**（对象创建）、**结构型**（对象组合）、**行为型**（对象交互）

**创建型模式（Creational）**：

1. **单例（Singleton）**：确保一个类只有一个实例，并提供全局访问点
   - 用途：配置管理、连接池、线程池、日志管理器
   - 实现要点：私有构造函数 + 静态实例变量 + 静态获取方法
   - **线程安全实现**：
     - 饿汉式：类加载时初始化（简单，线程安全，但可能过早占用资源）
     - 懒汉式 + 双重检查锁定（DCL, Double-Checked Locking）：需要 volatile 禁止指令重排
     - 静态内部类（Initialization-on-demand holder idiom）：推荐，类加载机制保证线程安全
     - 枚举（Java）：最简单，天生线程安全且防序列化和反射攻击

2. **工厂方法（Factory Method）**：定义创建对象的接口，让子类决定实例化哪个类
   - 简单工厂：一个工厂类根据参数决定创建什么产品（不是 GoF 23 种，但常用）
   - 抽象工厂（Abstract Factory）：创建一系列相关/相互依赖的对象家族（如创建 UI 组件的 MacFactory / WindowsFactory）

**结构型模式（Structural）**：

3. **适配器（Adapter / Wrapper）**：将一个类的接口转换成客户期望的另一个接口，使不兼容的类能协同工作
   - 例：用老接口适配新需求、Java Collections 中的 `Arrays.asList()`
   - 有类适配器（继承）和对象适配器（组合，更推荐）两种

4. **装饰器（Decorator）**：动态地给对象添加额外职责，比继承更灵活
   - 例：Java I/O 流（`new BufferedInputStream(new FileInputStream(...))`）
   - 特点：装饰器类与被装饰对象实现相同接口，持有被装饰对象的引用

**行为型模式（Behavioral）**：

5. **观察者（Observer / Publish-Subscribe）**：一对多依赖，一个对象状态改变，所有依赖者收到通知并自动更新
   - 例：MVC 中 Model 变化通知 View 更新、事件监听机制、消息订阅系统
   - 松耦合：被观察者不知道观察者具体是谁，只知道观察者接口

6. **策略（Strategy）**：定义一系列算法，封装起来并可互换使用
   - 例：排序算法（冒泡/快排/归并）、压缩算法（ZIP/RAR/7z），运行时可切换
   - 组成：策略接口、多个具体策略实现类、上下文（持有策略引用）

7. **模板方法（Template Method）**：定义算法骨架，将某些步骤延迟到子类实现
   - 例：JUnit TestCase 的 setUp() / tearDown() / runTest()
   - 与策略模式的区别：模板方法是继承（静态复用代码结构），策略是组合（动态切换算法）

**SOLID 设计原则**（模式背后的原则）：
- **S - 单一职责**：一个类只做一件事
- **O - 开闭原则**：对扩展开放，对修改关闭
- **L - 里氏替换**：子类可以替换父类不出错
- **I - 接口隔离**：客户不应该依赖它不需要的方法
- **D - 依赖倒置**：依赖抽象（接口），不依赖具体实现类

**问题 2：在项目中遇到的最大困难是什么？你是怎么解决的？**

**答题要点**：

**选择合适的困难**：
- ✓ 技术困难（如性能瓶颈、并发 bug、算法难题）：展现技术能力
- ✓ 设计困难（如架构重构、模块解耦）：展现设计思维
- ✓ 资源限制困难（如算力不够、数据集太小）：展现创造力

**结构化回答**：

4. **最终方案**：最终怎么解决的？为什么这个方案有效？
   - 例："重构查询逻辑，将 N+1 查询改为 JOIN；加 Redis 缓存热点数据；加连接池限制数据库并发；最终 95 分位响应时间 80ms"

5. **经验教训**：从中学到了什么？
   - 例："理解了数据库索引原理和查询优化的重要性，学会用性能分析工具定位问题"

**问题 8：你认为研究生和本科生最大的区别是什么？**

**答题要点**：

这个问题考察你对研究生身份的理解：

**从学习到研究**：
- 本科：学习已有的知识（"学别人做过的菜"）
- 研究生：创造新的知识（"做别人没做过的菜"）
- 从"被动接受"到"主动探索"

**从广度到深度**：
- 本科：多门课程，广泛涉猎
- 研究生：聚焦某个具体问题，深入钻研

**思维方式变化**：
- 本科：解决有标准答案的习题
- 研究生：解决没有标准答案的研究问题，需要自己定义问题、设计方法、评估效果

**能力要求变化**：
- 本科：考试能力、实现能力
- 研究生：文献阅读能力、独立思考能力、提出问题能力、写作/演讲能力

**自主性要求**：
- 本科：有课程大纲、有考试范围、有明确标准
- 研究生：导师给出方向，具体怎么做需要自己探索（导师更像顾问而非监工）

**回答时可以结合自己本科经历和对研究生生活的理解，体现成熟思考**。

**问题 10：你有什么问题要问我（面试官）吗？**

**答题要点**：

**一定要准备问题！**没有问题会被解读为对这个机会不关心或缺乏思考。

**可以问的好问题**：

**关于学术/研究**：
- "我对 XX 方向很感兴趣，请问老师/学长对这个方向的入门有什么推荐的学习路径/经典论文吗？"

### 三、计算机学习相关（11-15）

**问题 11：你最喜欢/最擅长的一门计算机课程是什么？为什么？**

**答题要点**：

**选择策略**：选一门你真的学得深入、能讲出深度理解的课程。

**推荐课程**（选择后准备好深度内容）：

- **数据结构/算法**：可以讲某个数据结构的设计哲学、算法复杂度分析、某个算法的巧妙之处
- **操作系统**：可以讲虚拟内存设计、进程调度策略、文件系统设计
- **计算机网络**：可以讲 TCP 的可靠传输设计、分层架构的哲学
- **编译原理**：可以讲词法/语法分析、代码生成、优化技术
- **计算机组成原理**：可以讲流水线设计、缓存层次结构

**回答结构**：

1. **你选哪门课**（+ 简单说为什么喜欢）

2. **你从这门课中学到了什么**（技术内容层面）：
   - 例："我最喜欢操作系统。它让我理解了计算机资源是如何被高效管理的——从 CPU 调度到虚拟内存，每一个机制都是在解决一个具体的工程问题：如何让多个进程'看起来'同时运行？如何让有限的内存'看起来'无限大？"

3. **这门课对你的启发/改变**（思维方式层面）：
   - 例："让我理解了'抽象'和'层次'的力量——硬件被抽象成资源，操作系统又被抽象成系统调用，应用程序站在这两个抽象之上构建。这种分层思想在计算机网络、数据库、分布式系统中反复出现。"

4. **你做了什么额外的学习/项目来深入**（证明你真的感兴趣）：
   - 例："我还自己实现了一个小型的 xv6-like 操作系统内核，加深了对系统调用和进程管理的理解。"

**问题 12：你最不擅长/最不喜欢的计算机课程是什么？为什么？怎么改进的？**

**答题要点**：

**注意**：这是一个危险的问题，诚实但不要暴露致命弱点。

**推荐策略**：

1. **选一个非核心但确实有难度的课程**（不要选数据结构/操作系统这种核心课）

3. **重点讲你如何改进/现在如何看待**：

4. **展现成长心态**：不擅长的领域你做了什么来改进？
   - 看公开课、看经典书、做项目实践、请教同学

**关键**：把一个看似负面的问题，转化为展示你"反思能力"和"成长心态"的机会。

**问题 13：从本科学习到现在，你印象最深的一个计算机概念/原理是什么？**

**答题要点**：

这是一个很好的展示你深度思考能力的问题。

**推荐回答方向**：

**方向 1：抽象与分层（最有哲学意味的答案）**
- 计算机科学最重要的思想就是分层与抽象
- 例："我最深的概念是'抽象'。从硬件到操作系统到应用层，每一层都在隐藏复杂性、提供简洁接口。CPU 把电路细节抽象成指令集；操作系统把硬件资源抽象成系统调用；编程语言把机器码抽象成语义；数据库把磁盘 IO 抽象成 SQL。整个计算机科学的历史，就是不断构建更高层抽象的历史。"

**方向 2：缓存与局部性（最实用的答案）**
- "局部性原理和缓存。从 CPU 的 L1/L2/L3 cache，到操作系统的 page cache，到数据库的 buffer pool，到 CDN，到浏览器缓存——整个计算机体系结构都是围绕缓存构建的。本质都是利用时间局部性（刚访问的数据可能再访问）和空间局部性（附近的数据可能被访问），用小容量的快速存储弥补大容量慢速存储的性能差距。"

**方向 3：时间/空间权衡（最通用的答案）**
- "很多计算机问题最终都是时间和空间的权衡。哈希表用额外空间换取 O(1) 查找；B 树用树高换取每个节点的低扇出；动态规划用空间存中间结果避免重复计算；甚至在算法竞赛中，很多优化都是在用更多内存换取更快的速度，或者反过来。"

**方向 4：分布式系统 CAP 定理（最前沿的答案）**
- 适合对分布式系统有深入理解的同学
- "CAP 定理让我理解了为什么分布式系统这么难——一致性、可用性、分区容错不可兼得。在真实系统中，我们必须做出取舍：CP 系统牺牲可用性（如 ZooKeeper），AP 系统牺牲强一致性（如 Cassandra）。这让我开始理解工程不是追求完美，而是在约束中做权衡。"

这个问题考察你的**技术视野**和**独立思考能力**。

**问题 17：你最大的优点和缺点分别是什么？**

**答题要点**：

**优点**：选一个和计算机专业相关的优点，用具体事例证明
- 例："我最大的优点是动手实践能力强。学一门技术时我不会只看书，一定会跟着做一个项目。比如学习分布式系统时，我就跟着 MIT 6.824 课程，用 Go 实现了一个简单的 MapReduce 和 Raft。"

**缺点（最关键的部分）**：**不要**说自己完美，也不要说致命缺点（如"我数学不好"、"我代码能力差"）。说一个**真实但不致命、且你在改进**的缺点。

**好的缺点例子**：

1. **过度追求完美 / 有时花太多时间在细节优化上**
   - 说明：有时为了让代码更优雅/性能更好，会花时间反复重构，导致整体进度受影响
   - 改进：学习区分"足够好"和"过度优化"，用 TODO 和时间盒管理

2. **有时过于独立 / 不善于及时寻求帮助**
   - 说明：遇到问题倾向于自己死磕，花了很多时间才意识到应该问别人
   - 改进：设定时间阈值，如果 X 小时内无法解决就去请教别人

3. **兴趣太多 / 有时会分散精力**
   - 说明：对很多技术都感兴趣，有时同时学太多东西，导致进度都不够快
   - 改进：用优先级排序，聚焦最重要的 1-2 件事

4. **表达能力有待提高 / 有时技术想法难以向非技术人员解释清楚**
   - 说明：有时写文档或讲解技术时，不自觉假设听众有同样的背景知识
   - 改进：写博客、做分享练习，主动寻求反馈

**回答缺点的黄金法则**：
- 真实可信（不要说"我最大的缺点是太追求完美"这种假大空的话）
- 不影响核心能力（不要说技术能力差）
- 你已经在改进 / 有具体的改进计划

**问题 18：在团队项目中你通常扮演什么角色？遇到团队冲突如何处理？**

**答题要点**：

**角色**：可以根据你实际情况选一个：
- **技术负责人 / 架构师**：负责技术方案设计、核心模块实现、代码 review
- **执行者 / 核心开发**：负责具体模块开发，保证交付质量
- **协调者 / 项目经理**：负责分工、进度跟踪、沟通协调
- **多面手 / 救火队员**：哪里需要去哪里

**团队冲突处理**：

推荐思路（参考"关键冲突"模型）：

1. **先理解事实**：不是简单的谁对谁错，而是弄清分歧点（需求理解不同？技术方案不同？个人习惯不同？）
2. **区分不同类型的冲突**：
   - **技术冲突**（最常见）：用数据和事实说话，做 A/B 测试或原型验证，不要变成个人争辩
   - **进度冲突**：用优先级和截止日期协调，必要时削减 scope
   - **人际冲突**：最需要谨慎处理，私下沟通、寻求第三方调解
3. **对事不对人**：聚焦问题本身，不攻击对方人格
4. **寻求双赢**：不是"我的方案 vs 你的方案"，而是"我们一起找最好的方案"
5. **当自己错了，爽快承认**（体现胸怀和成熟）

**可以准备一个具体的例子**：在某个团队项目中遇到过什么冲突，怎么分析、怎么处理、最终结果如何。

**问题 19：如果这次考研/保研没有成功，你有什么备选计划？**

**答题要点**：

这是一个压力测试类问题，考察你的**抗挫能力**和**规划能力**。

**推荐回答思路**：

1. **表达自信**：先表达对自己准备的信心（但不要太自负）
   - 例："我对自己的准备和表现还是有信心的，希望能有机会在南大继续学习。"

2. **给出备选（体现成熟规划）**：

**可以选择的趋势方向**（选 1-2 个深入）：

1. **大语言模型 / 生成式 AI**：
   - LLM 从通用模型向垂直领域/Agent 演化
   - RAG、工具调用、多模态、推理能力提升
   - 小模型 + 蒸馏/量化：大模型能力下放
   - 应用层创新：AI 编程助手、AI 搜索、AI 办公、AI Agent

2. **AI 基础设施（AI Infra）**：
   - 训练：分布式训练框架、混合精度、FlashAttention 等算子优化
   - 推理：vLLM、TensorRT-LLM、K/V cache 管理、Speculative Decoding
   - GPU 集群调度：K8s GPU 管理、资源隔离、成本优化
   - 向量数据库 / RAG 架构

3. **系统与架构方向**：
   - Rust 逐渐成为系统编程新选择（Linux 内核、数据库、编译器）
   - eBPF 在内核可编程性上的应用（可观测性、网络、安全）
   - Serverless 架构演进
   - WebAssembly（WASM）带来的跨平台运行时

4. **数据库与存储**：
   - 云原生数据库（Snowflake、TiDB、CockroachDB 模式）
   - 向量数据库兴起（Milvus、Pinecone、Weaviate）
   - HTAP（混合事务分析处理）
   - 数据湖 / lakehouse 架构

5. **安全与隐私**：
   - 大模型安全（对齐、越狱、数据泄露防护）
   - 零信任架构
   - 隐私计算（联邦学习、同态加密、可信执行环境）

6. **其他**：
   - 量子计算（虽远但长期值得关注）
   - 边缘计算 + 5G/6G
   - 碳中和驱动的绿色计算

**回答结构**：
1. **你最关注的 1-2 个趋势是什么**
2. **为什么你认为它重要**（技术突破 / 商业价值 / 社会影响）

## 🔬 第四部分：科研项目问答要点

### 科研项目问答通用框架

**项目自述框架（准备 3 分钟版本和 1 分钟版本）**：

```
**项目名称**（一句话定位）
**背景与动机**（解决什么问题？为什么重要？现有方法的局限？）
**核心思路**（你用了什么方法/技术？创新点在哪里？）
**技术细节**（架构图/关键算法/核心代码片段）
**实验与评估**（实验设置、对比基线、关键指标、消融实验）
**结果与贡献**（你解决了问题吗？效果如何？有什么创新贡献？）
**局限与改进**（有什么不足？未来可以怎么改进？）
```

**常见追问准备**：

1. **为什么选这个方法而不是 X 方法？**（技术选型的理由、trade-off 分析）
2. **你的方法的核心创新到底是什么？**（和现有工作的区别）
3. **如果 [某种极端情况] 会怎么样？**（考察对方法边界和适用场景的理解）
4. **这个方法在 [某个具体应用场景] 可以用吗？**（考察迁移应用能力）
5. **实验的基线设置是否合理？**（实验严谨性）
6. **你这个工作和 [某经典论文] 的关系是什么？**（文献视野）
7. **如果让你重新做这个项目，你会做什么不同？**（反思能力）

### 应对科研问题的心态

- **诚实**：真的不知道就说"这是一个很好的问题，我之前没有仔细考虑过，我的初步想法是..."，不要瞎编
- **谦虚**：不要说自己的工作多么厉害，客观陈述事实和成果
- **自信**：对自己做过的工作有信心，讲清楚就好
- **好奇**：对面试官的追问表现出兴趣，体现乐于讨论

### 面试后建议

1. **复盘**：面试结束后立即记录被问到的问题（尤其是不会的），为后续面试准备
2. **补漏**：面试中暴露出的知识盲区，尽快补全
3. **迭代**：回答得不好的问题重新组织回答框架
